### Overview and Evaluation by Dimension

This paper presents a formal transaction-log model for Git-compatible source control (`YonedaRepo`), adapting lakehouse log semantics (Delta Lake) and classical optimistic concurrency control (Kung and Robinson; Bernstein, Hadzilacos, and Goodman) to server-side commit preparation and branch landing. The core architectural insight—separating content-addressed commit construction from serialized ref updates while treating file-level write-write overlaps as three-way merges rather than aborting under first-committer-wins—is sound, well-motivated, and clearly connected to the implementation in Appendix A. The candor regarding implementation gaps (batch write skew in Theorem 7.3, unchecked base versions in Assumption 6.1, and unchecksummed checkpoint ref maps in Theorem 5.1) is a significant strength.

#### 1. Mathematical Correctness
The foundational results on tree rewrite cost (Proposition 4.3), access overlap (Lemma 4.4), log replay determinism (Theorem 5.1), tamper evidence (Proposition 5.2), first-parent ref advancement (Lemma 5.3, Theorem 5.4, Corollary 5.5), snapshot immutability (Theorem 5.6), and candidate independence (Theorem 6.6, Proposition 6.9) are correct. However, two main serializability results—Theorem 6.3 and Proposition 7.4—state conclusions that are stronger than what their hypotheses and proofs establish:
* **Theorem 6.3 (lines 491–512)** omits the hypothesis that $v_1 < \dots < v_m$ are *all* entries on ref $r$ in the interval under consideration (excluding interleaved batch merges or imports), and blurs the writer's commit $c_i$ with the platform merge commit $m_i$ actually appended to the log in the `Rebase` case.
* **Proposition 7.4 and its commentary (lines 658–667)** claim that enforcing $(\R_j \cup \W(c_j)) \nmeets \W(c_i)$ for $i < j$ yields "the serial history in ticket order" to which Theorem 2.1 of Bernstein, Hadzilacos, and Goodman applies. Because a batch can include members validated as `Merge` against the pre-batch head $H_0$, and line-level three-way merges are not conflict-serializable (as Section 6.2 explicitly notes on line 533), the batch history is only equivalent to *sequential landing* in ticket order, not a serial execution unless no member required a line-level merge.

#### 2. Clarity
Definitions and theorem statements are generally crisp, and the contrast between two-sided scheduling independence and one-sided landing validation (Section 6.4) is explained well. Clarity suffers where the formal model conflates types (e.g., $T(c)$ as both a list of operation/blob tuples and a set of location nodes) or leaves implicit how a platform merge commit's write set $\W_{v_i}$ and refined write set $\W^{\rho}_{v_i}$ are derived when the authority verifies rather than recomputes a merge.

#### 3. Completeness
The paper is self-contained for the single-ref log and concurrency model, but it defers several load-bearing pieces to companion manuscripts: garbage-collection safety of hidden refs (Part II, Proposition 12.1), transitive symbol-reference expansion for read sets (Part II, Section 10), and capacity/latency modeling of the per-repository authority (Part III, Sections 3–6). In addition, the empirical evaluation in Section 8 relies on local runs whose raw outputs were not preserved (line 753) and small hosted runs ($n = 20$ edits from a single client machine) with conflicting numbers across runs and design notes.

#### 4. Logical Structure
The progression from motivation (Section 2) and system architecture (Section 3) to formal definitions (Section 4), log invariants (Section 5), concurrency control (Section 6), and batching (Section 7) is logical. However, Section 7 (the land combiner) introduces a new execution path that invalidates Invariant I8 (Table 3, line 705) before Section 7 is even summarized in the invariant table, and several subsections open or close with one- or two-sentence signposting bridges rather than substantive claims.

#### 5. LaTeX Quality
The manuscript compiles cleanly in structure, uses `booktabs` and `tabularx` appropriately, and formats math definitions consistently. However, it contains template leftovers in comments, loads multiple unused packages (`graphicx`, `xcolor`, `listings`, `cleveref`) and environments (`remark`), defines duplicate `\label`s on single definitions, omits non-breaking ties (`~`) before numbers, uses hyphens (`-`) instead of en-dashes (`--`) in all bibliography page ranges, and leaves internal tracking comments (`% M60`, `% S-1`, etc.) throughout the source.

#### 6. Prose Quality and House Style
The prose is direct and avoids heavy jargon, but it repeatedly violates three rules of the house style:
1. **One identifiable claim per paragraph**: Several expository paragraphs (most notably lines 312, 395, 457, and 514) pack three to five distinct claims—spanning formal theory, literature comparisons, and Cloudflare implementation mechanics—into a single block.
2. **Findings stated directly before qualification**: Paragraphs discussing limitations of theorems (e.g., lines 351, 395, 514) frequently open with meta-commentary or qualifications before stating the concrete boundary of the result.
3. **No filler or signposting**: Short signposting paragraphs and sentences appear throughout (e.g., lines 81, 124, 191, 305, 326, 338, 366, 466, 579, 726).

### Weakest Three Paragraphs and Model Rewrite

#### Weakest Paragraph 1 (Line 312)
> `Assumption~\ref{ass:tlsc:atomic} is the serialized-authority property and the only property of the execution platform the proofs use. Any store with serializable, all-or-nothing transactions over the authority's state satisfies it. A weaker store suffices for the log alone: if appending version $n+1$ is a put-if-absent and every command re-reads the log tail it validates against, Delta's argument applies \cite{armbrust2020delta}. In the reference implementation, a Durable Object processes one request at a time and its synchronous transaction API is all-or-nothing \cite{cfdoconcepts,cfdosqlite}; the authority's dispatcher wraps every command in that API and turns any error into a rollback, and the authority's crate calls only its SQL store interface (Appendix~\ref{app:tlsc:evidence}). Under the assumption, the history of the authority's database is a sequence of committed command executions, and we may reason about each command as a function from one database state to the next. The authority is then a state machine in Schneider's sense: its commands are deterministic and each executes atomically with respect to the others \cite{schneider1990}. For the log, the assumption gives exactly the contract Delta Lake states for catalog-managed tables, where a catalog ``must not ratify version $v$ until it has ratified version $v-1$, and it must ratify version $v$ at most once'' \cite{deltaprotocol}.`

* **Why it fails the house style**: This 215-word paragraph contains four separate claims: (1) which storage primitives satisfy Assumption 4.10 and how put-if-absent suffices for the log alone; (2) how Cloudflare Durable Objects and `transactionSync` realize the assumption in code; (3) how the assumption reduces the authority to a deterministic state machine in Schneider's sense; and (4) how it matches Delta Lake's catalog ratification contract. Jumping from abstract storage requirements to Cloudflare implementation details and then back to formal state-machine semantics breaks argumentative flow.

#### Weakest Paragraph 2 (Line 395)
> `Corollary~\ref{cor:tlsc:nolostupdate} says that the history of a ref exhibits no lost update, phenomenon P4 of Berenson and colleagues \cite{berenson1995critique}: on the ref item, the compare-and-swap plays the role of their first-committer-wins rule. At the level of files the system does something different, which Section~\ref{sec:tlsc:isolation} discusses. Corollary~\ref{cor:tlsc:nolostupdate} is where the compare-and-swap does its work. A writer whose commit was built on a stale head cannot replace the head, because the fast-forward path requires the first parent to equal the current value; it must go through validation and a merge. Undoing a landed change is itself a new commit: post-land repair proposes a revert commit, and break-glass lands only fast-forwards. Refs are never rewritten. The result is a property of the code at the stated commit, not of the log format, which reserves kinds for ref moves and deletions. If an owner-reset operation were added, Theorem~\ref{thm:tlsc:forward} would hold only between resets, and validation already treats such entries as opaque.`

* **Why it fails the house style**: It mixes three distinct topics: database isolation phenomena (Berenson's P4 on refs vs. files), operational mechanics of stale commits and reverts, and a qualification on Theorem 5.4 regarding unused log-entry kinds (`ref_move`, `ref_delete`). It also includes pure signposting ("At the level of files the system does something different, which Section 6.3 discusses") and repetitive filler ("Corollary 5.5 is where the compare-and-swap does its work").

#### Weakest Paragraph 3 (Line 514)
> `Theorem~\ref{thm:tlsc:serializability} is an instance of a standard result, and the places where our setting differs from the source's assumptions show where the guarantee stops. It covers declared reads only, whereas the theory, and Delta's conflict checker, use the reads a transaction actually performs. It holds per ref, because entries on other refs write other data. For writes it covers the FastForward and Rebase outcomes; the Merge outcome has the weaker description of Proposition~\ref{prop:tlsc:merge}. And it assumes the platform's merge is the three-way merge. The authority does not recompute the merge; it checks that the merge commit has the right parents, was built by the platform principal, and touches only paths that the merged work touched. Content correctness rests on the merge code, whose evidence is the differential test of Section~\ref{sec:tlsc:evidence}.`

* **Why it fails the house style**: The opening sentence is meta-discourse signposting that states no finding. The remainder of the paragraph is a four-item list of unrelated caveats (declared vs. actual reads, single-ref scope, `FastForward`/`Rebase` vs. `Merge`, and adapter vs. authority verification of merges), ending with a nominalized reference ("whose evidence is the differential test of Section 8").

#### Model Rewrite (of Line 514)
*(Note: To satisfy "one identifiable claim per paragraph," the scope boundaries of Theorem 6.3 and the trust boundary of merge computation should either be separated or unified around the single claim of what Theorem 6.3 guarantees and where that guarantee stops.)*

> Theorem~\ref{thm:tlsc:serializability} guarantees conflict-serializability on a single ref only for `FastForward` and `Rebase` landings relative to declared read sets, assuming that the adapter's merge implements a three-way merge. Unlike classical serializability theory \cite{bhg1987} and Delta Lake's conflict checker \cite{deltaconflictsrc}, which track all data a transaction actually reads, the authority validates only the read set the writer declares and ignores entries on other refs. When writes overlap, landing falls back from `Rebase` to a line-level `Merge` governed by Proposition~\ref{prop:tlsc:merge} rather than serializability. Even on the `Rebase` path, the authority verifies only that the merge commit was built by the `platform:merge` principal, names the expected parents, and modifies only paths in the merged commit's write set; that the merged tree equals the three-way merge rests on the stateless merge implementation tested in Section~\ref{sec:tlsc:evidence}.

### Structured Feedback by Severity

#### Critical Issues
*No fatal flaws invalidate the core model or require outright rejection; however, two mathematical gaps in the serializability proofs (C1 and C2) mean that Theorem 6.3 and Proposition 7.4 do not hold as stated and require major revision before the paper is publishable.*

* **C1. Theorem 6.3 omits hypotheses on intervening entries and conflates the writer's commit with the platform merge commit (lines 491–512).**
  * **Line 493 & Line 499**: The theorem states: "Let landings on $r$ be appended at versions $v_1 < \dots < v_m$, each landing one commit $c_i$... If every landing in the sequence was validated as FastForward or Rebase, the history of $r$ is equivalent to the serial execution of $c_1, \dots, c_m$ in log order." This is false if $v_1, \dots, v_m$ is merely a subsequence of the entries on $r$ (for example, if a batch landing or another commit landed on $r$ between $v_i$ and $v_{i+1}$). You must specify that $e_{v_1}, \dots, e_{v_m}$ are *all* entries naming $r$ in $(v_0, v_m]$, and that each is a single-commit landing.
  * **Lines 497, 509, 511**: In the `Rebase` case (Part 3), the commit installed as $n_{v_i} = \Snap{v_i}(r)$ is not $c_i$, but a platform merge commit $m_i$ with parents $(\Snap{v_i-1}(r), c_i)$. Definition 4.12 (line 330) defines appending a commit as setting $n_{n+1}$ to that commit and recording its touched paths. Thus, subsequent landings $j > i$ validate against $\W_{v_i} = T(m_i)$ and $\W^{\rho}_{v_i} = \W^{\rho}(m_i)$, not $\W(c_i)$ and $\W^{\rho}(c_i)$. To close the proof on line 511, you need to state explicitly that for a `Rebase` merge commit $m_i$, $\Delta(m_i) = \Delta(c_i)$, $T(m_i) = \W(c_i)$, and $\W^{\rho}_{v_i} = \W^{\rho}(c_i)$.
* **C2. Proposition 7.4 and its discussion conflate equivalence to sequential landing with conflict-serializability (lines 658–667).**
  * **Lines 660, 664, 667**: Proposition 7.4 shows that if $(\R_j \cup \W(c_j)) \nmeets \W(c_i)$ for all $i < j$ in ticket order, the octopus merge produces the same tree as landing $c_1, \dots, c_k$ one at a time in ticket order. However, the combiner accepts members whose validation against the head $H_0$ returned `Merge` (line 611, line 636). If any member $c_j$ required a line-level three-way merge against $H_0$ (because an entry prior to $H_0$ modified the same file), neither the batch landing nor the sequential landing is conflict-serializable (as Section 6.2 proves on line 533). Therefore, claiming on line 664 that "[t]his is the serial history in ticket order" and on line 667 that "Theorem 2.1 of Bernstein, Hadzilacos and Goodman applies" is incorrect unless every member in the batch was validated as `Rebase` (or `FastForward`) against $H_0$.
  * **Line 660**: Proposition 7.4 checks $\R_j \nmeets \W(c_i)$ using the *unrefined* path-level write set $\W(c_i)$, whereas sequential validation (Definition 4.11, clause 1, line 319) checks $\R_j \meets \W^{\rho}(c_i)$ using the *refined* symbol-level write set. Consequently, Proposition 7.4's rule is sufficient for sequential non-conflict, but strictly coarser when symbol refinement is active. State this distinction explicitly.

#### Major Issues

* **M1. Unchecked base version allows `Proposal::check` to return `FastForward` on stale parents during merge verification (lines 317–324, 478, 636).**
  In Definition 4.11 (line 320), validation returns `FastForward` whenever $\Later(P) = (e_v : b < v \le n,\ r_v = r)$ is empty, without checking $\fp(c) = \Snap{n}(r)$. Line 478 notes that a writer may pass a custom parent $\fp(c)$ and base version $b$, and the authority checks only $b \le n$. If a writer passes $b = n$ with an old parent $\fp(c) \neq \Snap{n}(r)$, direct landing refuses because $\fp(c) \neq \Snap{n}(r)$, but if the commit enters the merge path (`verify` or `verify_octopus`), re-running `Proposal::check` at version $n$ sees $\Later(P) = \varnothing$ and returns `FastForward`, which verification accepts (line 636), bypassing all conflict checks between $\fp(c)$ and $\Snap{n}(r)$. Definition 4.11 should require $\fp(c) = \Snap{b}(r)$ (or `FastForward` should check $\fp(c) = \Snap{n}(r)$).
* **M2. Assumption 6.2 (Sound refinement) for platform merge commits relies on unverified adapter output (lines 209, 480, 514).**
  Line 480 claims that "Assumption 6.2 holds at path granularity by Lemma 5.3 and the inclusion $\Delta(c) \subseteq T(c)$." However, line 209 establishes $\Delta(c) \subseteq T(c)$ only "for every commit the platform prepares" via the authority's `prepare` command. Platform merge commits (and `import` commits) are not built by `prepare`; as line 514 states, the authority does not recompute the merge and only checks that the merge commit's declared touched paths are a subset of the merged work's touched paths. If the authority does not diff $\tree(m)$ against $\tree(\fp(m))$ itself, then $\Delta(m) \subseteq T(m)$ is an assumption about the stateless merge compute, not a theorem of Lemma 5.3.
* **M3. Type mismatch between $T(c)$, $\Delta(c)$, and $\W(c)$ (lines 206, 209, 247, 267).**
  Definition 4.2 (line 206) defines $\Delta(c)$ as a set of paths, but defines $T(c)$ as a list of records "each with an operation (add, modify or delete) and its old and new blob." Line 209 then writes $\Delta(c) \subseteq T(c)$, and Definition 4.5 (line 247) writes $\W(c) = T(c)$ where $\W(c)$ is a set of location nodes in $\Loc$. Define $T(c)$ cleanly as the set of path nodes recorded with $c$ (or define a projection from change records to path nodes) so the set inclusions and overlap relations are well-typed.

  Line 51 subtitles this paper `Part I of \emph{Source Code as a Transactional Abstraction}`, whereas lines 948 and 953 cite Parts II and III as `Part II of \emph{Source Control as a Data System}` and `Part III of \emph{Source Control as a Data System}`. Unify the series title.
