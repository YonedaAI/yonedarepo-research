1 Introduction

Source code and source control are now transactional abstractions. A repository is a database whose state is a map from refs to immutable objects. A change is a transaction that reads part of the source and writes another part. Landing a change is a commit under optimistic concurrency control, a version of the repository is a snapshot, and everything computed from the source, from a search index to the Git commits of a branch, is a view kept consistent with a snapshot. A series of three papers lays the foundations for that view, and its results compose into ones that no single paper states: the Git commit of a branch can be built after a change lands without weakening any guarantee of the log, and in a reference realization the landing path built on that result landed every writer in each of six bursts of 1,000.

We argue that this is the next evolution in code, and that data went through the same evolution first. Data lakes began as files on object stores. Concurrent writers and derived computation made a directory of files an unreliable unit of state, and the field moved to tables with a transaction log, snapshots and optimistic concurrency [3, 21], with partitioned computation running over those snapshots [37]. Source control is now under the same pressure. Anthropic reports that its merge rate grew from about 2,500 code changes per day in May 2026 to more than 30,000 per day by September, and that source control became its largest development bottleneck [2]. Scion’s published design responds with server-side changesets in a write-ahead log and a ref update that is a compare-and-swap on one database row, separate from creating commits [2]. That is the move data made. Section 2 develops the argument and its limits.

The reason the move matters now is that the writers changed. A person clones, edits offline, pushes a finished commit and retries by hand when the branch has moved. An agent is always online, writes a few files against a head that moves while it works, and can state what it read and what it wrote. Many agents on one branch are many concurrent transactions. Git’s push protocol gives them a single compare-and-swap on a ref and leaves everything else, building the commit, deciding whether the change still holds, rebasing and retesting, on the client [19]. A transactional repository moves those decisions to the server, where they can be made from recorded read and write sets.

The series supplies three foundations. Part I gives the transaction model: a hash-chained log of ref changes, snapshots and checkpoints, backward validation of declared read and write sets, a serializability theorem, and the one place where the implemented group landing falls short of it [26]. Part II treats derived data as views over that log, maintained by partitioned jobs over immutable snapshots, and proves when incremental maintenance equals recomputation [27]. Part III builds the transaction system on cloud-portable primitives, measures it on Cloudflare as the reference realization, and models where its serialized authority saturates [28].

The composition rests on a choice of vocabulary. Part I states every correctness result over log entries, read sets, write sets and validation outcomes, never over Git objects. Part II shows that the Git commit of a branch is a deterministic view of the log. Together they imply that Git objects can leave the landing path without weakening the log’s guarantees, which turns the authority’s critical section into a validation query and an append. Part III’s capacity model then says what limits a branch: one serial call per batch rather than one per landing. The measurements follow that chain. Landing modes that built Git trees on the landing path failed under a burst of 1,000 writers, and the mode that appends changesets in batches landed all 1,000 in every run (Section 7).

The paper makes five contributions.

  1. A single model of a transactional repository over six primitives, with the correspondence to transactional tables made explicit (Section 3).

  2. A catalogue of the series’ principal theorems, each stated with its assumptions and the established result it instantiates (Section 4).

  3. Composition results: views consistent at a snapshot under any interleaving of landings and derivation jobs, Git semantics without Git on the landing path, batch capacity without loss of isolation, and reads served away from the authority without a change of meaning (Section 5).

  4. A treatment of agents as concurrent transactions, including the condition under which the serializability guarantee extends to a task’s information closure, and a map from the companion paper’s equations, propositions and predictions to the series (Section 6).

  5. A consolidated account of the measured evidence, with negative results, defects the analysis found, and the open problems that remain (Sections 7 and 10).

The reference implementation, YonedaRepo, is first-party work: the author designed and built it, and it is still being built. Terms such as “authority”, “land combiner” and “changeset landing” are this project’s names, not industry usage. Every claim about its code is tied to a file and commit in Appendix A or to the Part that makes it. Every measurement comes from the Cloudflare realization; none comes from a production deployment.

2 Precedent and pressure

2.1 Files to tables in data systems

A data lake that stores a table as a directory of files on an object store has no atomic unit larger than one object. A writer that adds and removes several files can be seen half done, two writers can interleave, and a job that computes over the directory has no name for the state it read. Delta Lake was built to give such tables ACID transactions over cloud object stores [3]. Its protocol answers with a log: “a table has a single serial history of atomic versions, which are named using contiguous, monotonically-increasing integers,” and each log file is the unit of atomicity [14]. A snapshot is computed by replaying the committed actions in ascending version order from a checkpoint no newer than the requested version [14].

The paper that introduced Delta Lake derives its isolation level from the commit step. A writer reads version \(r\) and then attempts to create log record \(r+1\) atomically, by put-if-absent, atomic rename or a coordination service, and because only one transaction can create each record, write transactions are serializable in increasing order of record identifiers [3]. Readers at a snapshot create no contention. The commit rate is bounded by the latency of the atomic step, several transactions per second on object stores, and the authors name a low-latency coordinator and batching as the remedies [3]. Whether a writer that retries at a later version is still correct depends on conflict checks, which the implementation states: a committing transaction fails if a concurrent commit added files that match its read predicates or removed files it read [11, 12]. Iceberg reaches the same structure by an atomic swap of a metadata pointer, and its specification makes the isolation level a property of what each writer chooses to validate [21].

Computation moved with the storage. Resilient distributed datasets are read-only, partitioned collections created only by deterministic operations, and a lost partition is recomputed from its lineage [37]. Over a snapshotted table, that model gives derived results a precise meaning: a result describes one version, and recomputing it from that version reproduces it.

2.2 Pressure on source control

Git already has immutable, content-addressed objects [18]. What it lacks is a transaction around a change: its atomic step is the compare-and-swap of a ref update. A push sends, for each ref, the old and new object identifiers, and the server updates the ref only if it still holds the old value [19]. Everything before that compare-and-swap happens on the client, and when the swap fails, all of it is stale. The cost of a lost race is a fetch, a rebuild, a retest and a retry, paid in full even when the competing change touched unrelated files (Part I, Section 2).

Agents raise both inputs to that cost. They multiply the number of concurrent writers on a branch, and they multiply derived work: checks on every candidate, search and symbol tables at every head, plans over symbol-level read and write sets. The Scion post reports a main-branch history of almost 100 GB and on the order of 25 million CI checkouts per day at one company [2]. These are one organization’s reported figures, used here as motivation and not as measurements of anything this series built.

2.3 The same move in Scion’s published design

We know Scion only from its published description [2]. Its changesets are created on the server as entries in a write-ahead log, each listing the files changed against its first parent. A ref moves by a compare-and-swap on a single Spanner row that is not involved in creating or fetching changesets. Derived data such as blame and path history are defined recursively over a changeset’s parents and computed by one generic mechanism. Read traffic passes through tiers that hold no long-lived state. Each element has a counterpart in the transactional-table design: changesets are log records, the ref row is the atomic step, derived data are views with lineage, and the tiers serve immutable objects. Scion’s design does not need Git trees to land a change, and it describes itself as not a general Git replacement [2].

2.4 Scope of the argument

Precedent constrains structure, not cost. The data-system precedent predicts that a repository under many concurrent writers will be organized as a log of atomic changes over immutable objects, with snapshot reads, validation at commit, and derived data defined per snapshot. It does not predict how fast such a system lands changes, and it does not show that the structure is necessary.

Three differences keep the analogy from being an identity, and the series treats each formally. The state of a repository is a map of refs, not a set of files, so a checkpoint is a ref map (Part I, Section 5.4). Two writers of one file can often both succeed through a three-way merge, which has no counterpart in a table, so the model is not snapshot isolation at file granularity (Part I, Section 6.3). And read sets are declared by the writer rather than observed by an engine, so serializability holds relative to what is declared (Part I, Theorem 6.4). The evidence of Parts I to III supports the thesis by showing that the structure carries over with proofs, that it can be realized on generic cloud primitives, and that its measured costs fall where the theory places them. It does not show production behavior or scale beyond the bursts that were measured.

The one property of the execution platform that the proofs use is that the authority’s commands behave as if executed one at a time, each committing all of its writes or none, with no network input or output inside a command (Part I, Assumption 4.14). Under it the authority is a state machine whose deterministic commands execute atomically with respect to one another [35], and it meets the contract that Delta’s protocol states for catalog-managed tables: a catalog “must not ratify version \(v\) until it has ratified version \(v-1\), and it must ratify version \(v\) at most once” [14]. 3.2 State, transactions and versions

We use Part I’s notation throughout. An object store \(O\) maps 160-bit identifiers to typed bytes and only grows (Part I, Definition 4.1). A log \(\mathcal{L}=(e_1,\dots,e_n)\) is a sequence of entries, each recording a version \(v\), a base version \(b<v\), a ref \(r\), its old and new values, the touched paths \(\mathsf{W}_v\), the declared read set \(\mathsf{R}_v\) and a chain digest (Part I, Definitions 4.8 to 4.10). The snapshot \(S_{v}\) is the ref map obtained by replaying \(e_1,\dots,e_v\) (Part I, Definition 4.11), and the branch state \(\sigma_v(r)\) is the tree obtained by applying, in log order, the effective changes of the entries that name \(r\) (Part I, Definition 8.1).

Definition 3.1 (Transactional repository). A transactional repository is a tuple \((O,\mathcal{L},A,\mathcal{V})\) of an object store, a log, a serialized authority \(A\) that alone appends to \(\mathcal{L}\) and satisfies Part I, Assumption 4.14, and a family \(\mathcal{V}\) of views. A change on ref \(r\) is \(\chi=(r,b,\mathsf{R},\mathsf{W},\Phi)\): a base version, a declared read set of accesses at path or symbol granularity (Part I, Definitions 4.4 and 4.6), a write set \(\mathsf{W}\) of file paths, which the authority may refine to symbols, and a map \(\Phi\) from each path of \(\mathsf{W}\) to its new content or its deletion. Landing \(\chi\) is one command of \(A\) that validates \(\chi\) against the later entries \(\mathrm{Later}(\chi)=(e_u)_{b<u\le n,\ r_u=r}\) and either refuses it or appends one entry (Part I, Definitions 4.15 and 4.16). A view \(V\in\mathcal{V}\) assigns to each version \(v\) and ref \(r\) a value \(V_v(r)\) that is a function of \(e_1,\dots,e_v\).

Validation has four outcomes (Part I, Definition 4.15). It returns Conflict when some later entry is opaque or has a refined write that overlaps \(\mathsf{R}\); otherwise FastForward when no later entry exists, Rebase when \(\mathsf{W}\) meets no later entry’s writes, and Merge, with the overlapping paths, when it does. The definition packages objects that Part I owns; it adds the view family so that Git, search and checks can be discussed as one kind of object.

Validation is closest to Delta’s Serializable level, under which reads and writes behave as if executed one by one, with the difference that the writer supplies the read predicates [13]. It is not the default WriteSerializable level, which orders only writes and lets an update commit past a concurrent insert it should have read [13]. The authority never reorders: the serial order is the log order, and a landing whose declared reads meet a later write is refused (Part I, Section 5.4).

3.3 Views

A view is anything computed from a version: a search index, a symbol table, the blame of a file, the result of a check, the Git commit of a branch. Part II makes the class precise. A content-local kind \(\delta\) has a map function \(f_\delta\) from a partition of a commit’s tree to a segment and a reduce \(\rho_\delta\) from the prefixed segments to a value, so that its value \(D_\delta(c)\) depends only on \(\tau(c)\) (Part II, Definitions 3.2 and 4.2). A system maintains the view incrementally when it answers from stored segments, filed under keys, and the maintained view is consistent at the snapshot when its answer equals \(D_\delta(c)\). A key function \(\kappa\) is sufficient for \(f\) when equal keys imply equal segments (Part II, Definition 5.1). History-dependent kinds, such as blame and path history, take the commit identifier as a sufficient key (Part II, Corollary 5.9).

The Git commit of a branch is a view of the same kind. Under changeset landing, the projection \(\Pi\) maps each log prefix and ref to a Git commit whose tree is \(\sigma_v(r)\) and whose first parent is the projection of the previous prefix (Part I, Definition 8.1 and Assumption 8.2; Part II, Definition 13.1). It is computed after the landing returns, by a projector that reads the log.

3.4 Cost

The cost model is stated over the primitives’ service times, with the Cloudflare measurements as one instantiation (Part III, Section 6). A serialization point serves one operation at a time for a given key, with service time \(s\); a batch point serves \(k\) operations in one service of time \(T(k)\) (Part III, Definition 3.1). For \(N\) agents with think time \(Z\), unloaded cycle time \(R_0\) and largest demand \(D_{\max}\) at any serialization point, throughput \(X(N)\) and cycle time \(R(N)\) obey the asymptotic bounds of operational analysis [15, 24]. The authority is the serialization point that every landing visits, and the land combiner or batched submission is the batch point in front of it.

4.1 The log

Theorem 4.1 (Replay and snapshots; Part I, Theorems 5.1 and 5.6). Let \(\mathcal{L}\) be well formed with current version \(n\) (Part I, Definition 4.10). Replaying \(e_{u+1},\dots,e_v\) from the true checkpoint at \(u\le v\le n\) returns \(S_{v}\) and the chain digest \(h_v\). For every later log \(\mathcal{L}'\) and every \(u\le n\), the snapshot at \(u\) computed from \(\mathcal{L}'\) equals the snapshot at \(u\) computed from \(\mathcal{L}\), and every object reachable from it is unchanged if present.

The theorem has a stated limit. A checkpoint is accepted when its digest matches the log, and the digest binds it to a position but not to its ref map, so a checkpoint whose map was altered with its digest kept is detected only when the altered ref is touched again (Part I, Theorem 5.1, second part). Delta specifies the remedy, a version checksum compared with the replayed state [14]; the counterpart is not implemented. Presence of objects needs its own assumption, that the store keeps every object reachable from a current ref (Part I, Assumption 5.7), and Part II proves that the platform’s release of hidden refs preserves it (Part II, Proposition 12.1).

In the implementation at cfa4845, no code path appends a ref move or a ref deletion, every append keeps the head as first parent or creates the ref, and therefore refs advance only along first-parent chains and every landed commit stays an ancestor of its branch (Part I, Lemma 5.3, Theorem 5.4 and Corollary 5.5). A read pinned at a version is a pure function of that version and takes no lock.

4.2 Isolation

Theorem 4.2 (Serializability relative to declared reads; Part I, Theorem 6.4). Let every entry naming \(r\) above a version \(v_0\) land a single commit with base at least \(v_0\), directly or through a platform merge whose parents are the previous head and that commit, and not as part of a batch. Assume the serialized authority (Part I, Assumption 4.14), a consistent base, \(\pi_1(c)=S_{b}(r)\) with the writer’s reads taken from \(\tau(\pi_1(c))\) (Assumption 6.1), and sound refinement of write sets to symbols (Assumption 6.2). Then for every landing, the contents of its declared read set are the same at its base and immediately before its entry. If every landing was validated as FastForward or Rebase, the history of \(r\) is conflict-serializable in log order.

Part I proves the theorem in two steps. A landing is the end step of Kung and Robinson’s serial validation, with start number \(b\), finish number \(n\) and the authority’s command as the critical section [23]. In the serialization graph over declared locations, write-write and write-read edges point forward in log order by construction, and a backward read-write edge is exactly a stale declared read, which validation refuses; the graph is acyclic and the serializability theorem applies [5].

Two boundaries matter for agents. The guarantee is relative to declared reads: a change that reads two files and declares neither can land beside a change that wrote the other, which is write skew of shape A5B (Part I, Example 6.6). And a Merge outcome lets two writers of one path both commit through a line-level merge, which is outside the read-write model; Part I describes it without a serializability claim, because no theorem makes clean diff3 merges commute [22]. For both reasons the system is not snapshot isolation at file granularity (Part I, Section 6.3).

Theorem 4.3 (Independence; Part I, Theorem 6.7). Let changes \(c_i\) and \(c_j\) share a base on ref \(r\), with read and write sets at path granularity, and let nothing else land on \(r\) in between. They satisfy \[\begin{equation} \mathsf{W}_i\not\bowtie(\mathsf{R}_j\cup\mathsf{W}_j)\quad\text{and}\quad\mathsf{W}_j\not\bowtie(\mathsf{R}_i\cup\mathsf{W}_i) \label{eq:syn:independent} \end{equation}\] if and only if, in both landing orders, the second to land is validated as Rebase.

Condition (1) is Eq. 1 of the companion paper [25], with set intersection replaced by overlap in the location tree so that a directory and a file inside it meet. The theorem gives the condition an exact operational meaning. Independence is a scheduling rule, evaluated before work runs and two-sided; validation is a safety rule, evaluated at landing against what landed and one-sided. A scheduler that ignores the condition stays safe, because validation still refuses stale reads, but it wastes the work of whichever item loses (Part I, Section 6.4). Coarsening any access to an ancestor, a symbol to its file or a file to its directory, keeps every Conflict and Merge and can only cost concurrency (Part I, Proposition 6.10).

4.3 Batches

Group landing amortizes the construction of a merge against the moving head, in the manner of group commit [16]. Part I proves that the combiner preserves the single-writer property of the append, whatever the state of its lease (Part I, Theorem 7.2), and then finds its anomaly.

Theorem 4.4 (Batch write skew and its repair; Part I, Theorem 7.3 and Proposition 7.4). At commit cfa4845, there are histories in which the combiner lands two commits \(c_a,c_b\) in one entry with \(\mathsf{R}_a\bowtie\mathsf{W}_b\) and \(\mathsf{R}_b\bowtie\mathsf{W}_a\), so that no serial order lets each read its declared set from the state the other leaves. If batch verification also requires, for the accepted members \(c_1,\dots,c_k\) in ticket order, that \((\mathsf{R}_j\cup\mathsf{W}(c_j))\not\bowtie\mathsf{W}(c_i)\) for all \(i<j\), then the batch produces the same branch state as landing the members one at a time in ticket order, and the history is conflict-serializable when every member validated as Rebase or FastForward.

The pair is a cycle of two anti-dependency edges in Adya’s direct serialization graph, phenomenon G2-item [1], and Fekete and colleagues show that every non-serializable snapshot-isolation history contains such a structure [17]. Validating each member against the committed log but not against the other members is certification in the style of snapshot isolation, and this is its expected failure. The rule is sufficient, not necessary: a certifier that accepts any batch whose serialization graph is acyclic accepts strictly more [5].

Part I then restates the model for changeset landing, in which a landing carries a base, a read set and file changes, is validated by path overlap against the log since its base, and is appended without building Git objects. Replay, immutability and serializability hold unchanged over log entries; the consistent-base assumption holds by construction because a changeset has no parent that could disagree with its base; and the first-parent and no-lost-update properties move from the ref table to the projected Git commits (Part I, Proposition 8.3).

4.4 Views

Theorem 4.5 (View consistency; Part II, Theorem 5.3 and Propositions 5.4 and 5.6). Let \(\kappa\) be sufficient for \(f_\delta\), let \(f_\delta\) be deterministic, let every put at a key write \(f_\delta\) of some partition with that key, and let gets return either nothing or a value previously put in full (Part II, Assumption 5.2). Then every incremental evaluation at every commit \(c\), under any interleaving of evaluators over any commits, returns \(D_\delta(c)\). If \(\kappa\) is not sufficient, some sequential order of two evaluations returns a wrong segment. With the segments of \(c'\) stored and none deleted, an evaluation of \(c\) runs at most one map task per partition of \(c\) whose key does not occur in \(c'\).

The segment store is a store of deep constructive traces: a result is filed under a hash of the task’s terminal inputs, and such traces are correct only for deterministic tasks [29]. Duplicate execution is harmless for the reason MapReduce gives [10], so last-writer-wins puts and at-least-once delivery cannot corrupt the store. The map-work bound is the incremental cost of a linear operator in DBSP, with the change taken to be the set of changed partitions [6], and content addressing reuses strictly more than recursion from parents, across reverts, cherry-picks and forks (Part II, Proposition 5.8).

Lemma 4.6 (Determinism of the Git projection; Part II, Lemma 13.2). Under collision resistance of object identifiers, the projected Git commit of main at version \(j\), computed by the rule of Part II, Definition 13.1, is a function of the log prefix \(e_1,\dots,e_j\). Two projectors that read the same prefix, on any replica and at any time, compute the same commit identifier.

Because the projected commit at \(j\) has the projected commit at \(j-1\) as first parent, the lemma discharges Part I’s Assumption 8.2, on which the first-parent and no-lost-update properties of changeset landing rest. Computing the projection at \(j\) from the projection at \(j-1\) rewrites only the trees on the changed paths (Part II, Proposition 13.3).

4.5 Capacity

Proposition 4.7 (Capacity bounds; Part III, Propositions 6.8 and 6.11). For a closed population of \(N\) agents with think time \(Z\) and unloaded cycle \(R_0\), throughput satisfies \(X(N)\le\min\{N/(R_0+Z),\,1/D_{\max}\}\), with knee \(N^{*}=(R_0+Z)/D_{\max}\). A batch point whose service of \(k\) operations takes \(T(k)=a+bk\) with \(a>0\) has capacity \(k/T(k)\), which increases strictly with \(k\).

The first part is Denning and Buzen’s bottleneck analysis, which needs only job flow balance and visit counts and service times that do not change with load [15]. Polling breaks the second hypothesis, since a waiting landing visits the authority for as long as it waits; Part III shows that pollers alone saturate the authority once their number exceeds the unloaded poll iteration divided by its service demand (Part III, Corollary 6.12). The second part is the arithmetic behind group commit and behind Delta’s advice to batch when the atomic step is slow [16, 3].

5 Composition of the parts

5.1 Consistent views under concurrent landing

Theorem 5.1 (Snapshot-consistent views). Let a repository land by changesets, with the serialized authority of Part I, Assumption 4.14 and collision-resistant object identifiers, and let the Git projection \(\Pi\) of main be computed by the rule of Part II, Definition 13.1. Let the object store keep every object reachable from a current ref (Part I, Assumption 5.7). Let \(\delta\) be a content-local kind whose key is sufficient for its map function and whose segment store satisfies Part II, Assumption 5.2, which includes determinism of the map function. Then for every version \(v\), with \(r\) the main branch:

  1. the tree \(\sigma_v(r)\) and the commit \(\Pi(e_1,\dots,e_v;r)\) are the same whenever and wherever they are computed, however many entries are appended later;

  2. every evaluation of \(\delta\) at \(\Pi(e_1,\dots,e_v;r)\), under any interleaving of landings, projection jobs and derivation jobs over any commits, returns \(g_\delta(\sigma_v(r))\), the value that recomputation from the snapshot gives.

Proof. For part 1, later appends leave \(e_1,\dots,e_v\) unchanged, because the authority only inserts log rows at new versions (Part I, Theorem 5.6 and Proposition 8.3(1)); \(\sigma_v(r)\) is a fold over that prefix, and \(\Pi\) of the prefix is a function of the prefix by Lemma 4.6. For part 2, write \(c=\Pi(e_1,\dots,e_v;r)\). Part II, Theorem 5.3 holds for every interleaving of evaluators over any commits, so every evaluation at \(c\) returns \(D_\delta(c)\). The kind is content-local, so \(D_\delta(c)=g_\delta(\tau(c))\) (Part II, Definition 4.2), and \(\tau(c)=\sigma_v(r)\) by the definition of a projection (Part I, Definition 8.1). Landings and projection jobs enter only through part 1: they append later entries or compute projections of other prefixes, and neither changes \(c\) or the segments that sufficiency ties to its partitions. Assumption 5.7 keeps the objects of \(c\) readable, so every map task an evaluation needs can run. ◻

The theorem says that a view is consistent at a snapshot, not that it is fresh. A query at “the head” of a branch is answered at the latest projected version, which trails the log by the projection delay; on the reference realization that delay had a p95 of 3.2 to 5.4 s in the six 1,000-writer bursts at fef94e7 (Section 7.6). During the delay the log already holds the landing and every view of main is behind it.

The theorem inherits every hypothesis it composes. In the reference implementation the search key is the bare subtree identifier, while segments record full paths, so the key is not sufficient and the conclusion fails for search on renamed or duplicated directories (Part II, Proposition 7.1). Part II gives two repairs that restore sufficiency and proves both. Symbol tables, keyed by extension and blob identifier, satisfy the weaker form in which every reader discards the stored path (Part II, Section 7).

5.2 Git semantics off the landing path

Proposition 5.2 (Git semantics without Git on the landing path). Assume a well-formed log, Part I, Assumptions 4.14 and 6.2, collision-resistant object identifiers, and, as in the implementation analyzed in Part I, Section 5.2, no command that deletes or resets the branch. A repository that lands changesets and builds the Git commits of main afterwards by the projection of Part II, Definition 13.1, keeps the guarantees that Part I, Proposition 8.3 lists: replay and snapshot immutability, serializability relative to declared reads, the exact meaning of Eq. (1), the description of merged writes, and the batch results. The first-parent and no-lost-update properties hold for the projected commits. Inside the authority, a landing whose paths are disjoint from every later entry reads no file content.

Proof. Part I, Proposition 8.3 establishes the carry-over under Assumption 8.2, and Lemma 4.6, which needs collision resistance, discharges Assumption 8.2. The first-parent property of projected commits follows because each entry naming main adds one first-parent step (Part I, Proposition 8.3(5)); a command that deleted or reset the branch would end that chain, which is why the hypothesis excludes one. A disjoint landing is validated by a query of the touched paths of the entries above its base and appended; only the merge path reads the three versions of a shared file (Part I, Section 3.6). ◻

The proposition is the theoretical reason the redesign could work. On every earlier landing path of the reference implementation, a landing that was not a fast-forward built a merge commit, with new tree objects on every changed path, before the authority appended the entry. Building Git objects there was a choice of that implementation, not a requirement of Git semantics: the requirement is that commits, branches, merges, diffs and logs keep Git’s meaning, and the projection supplies them. The price is the delay before a branch’s Git commit exists. The measured consequence appears in Section 7: with Git built while landing, 4 and 385 of 1,000 concurrent landings succeeded on one deploy, and with changesets appended and Git projected afterwards, all 1,000 did. The comparison varies the whole landing path, so it does not separate the cost of building Git objects from the other differences between the modes, such as polling.

5.3 Batch size and isolation

Proposition 5.3 (Batch size as a capacity parameter). Assume Part I, Assumptions 4.14 and 6.2, and let a branch land changesets in batches of at most \(k\) per authority command, with service time \(T(k)=a+bk\), \(a>0\). Let every member be validated against the log as in Part I, Definition 4.15. Suppose further either that members are appended one at a time in ticket order, so that each is validated against a log that includes the members appended before it, or that the command defers any member whose reads or writes meet the writes of a member accepted earlier in the batch. Then every batch history is equivalent to landing its accepted members one at a time in ticket order, conflict-serializable when every member validated as FastForward or Rebase, and the branch’s landing throughput is at most \(k/T(k)\), which increases strictly with \(k\).

Proof. In the first case each member is its own log entry, validated by Part I, Definition 4.15 against a log that already contains the earlier members, so the batch is a sequence of single landings and Theorem 4.2, carried over by Part I, Proposition 8.3(3), applies to it. In the second case the accepted members satisfy the condition of Part I, Proposition 7.4, which applies to batches of changesets by Part I, Proposition 8.3(6) and gives the equivalence and the serializability. The throughput bound is Part III, Proposition 6.11 for a batch point; the authority’s command is the serial step of every batch. ◻

Part III treated the batch size as having a semantic cost as well as a latency benefit, because Part I’s Theorem 7.3 made larger batches a larger window for write skew. Under either hypothesis of the proposition that cost disappears and \(k\) becomes a pure capacity parameter. The changeset path at dd6c9a8 satisfies the first hypothesis by construction, and the batch path merged at fef94e7 checks the second explicitly before routing each of up to 256 members (Part I, Section 8; Appendix A). The proposition also locates the measurable quantity: the batch call, not the landing. In the 1,000-writer run at fef94e7 that kept its detail, batches held 256 landings and the batch call took 308 ms at the median and 372 ms at p95, which bounds one branch at about 690 to 830 landings per second; the measured burst-span rates of 235 to 491 per second lie below that bound (Part III, Section 8.4). Those rates are averages over bursts of 2.7 to 4.3 s, not sustained rates.

5.4 Reads at a published head

Proposition 5.4 (Reads away from the authority). Assume collision-resistant object identifiers, and stores and caches that return either nothing or an object whose bytes hash to the requested identifier. A read of objects reachable from a commit identifier returns the same bytes from any such store or cache that holds them, and a read pinned at version \(v\) returns \(S_{v}\) or \(\Pi(e_1,\dots,e_v;\mathrm{main})\) from any replica of the log prefix or of the projection, without a call to the authority.

Proof. Objects are content-addressed, so under collision resistance an identifier determines its bytes (Part I, Definition 4.1), and a store that returns only verified objects cannot return other bytes; and reads at a commit are defined as reads of the objects reachable from it (Part I, Definition 4.13). The snapshot at \(v\) is a function of the prefix (Theorem 4.1), and so is the projection (Lemma 4.6). ◻

Snapshot reads were contention-free in the model from the start: they take no lock and no landing can invalidate them. In the realization they were not, because the authority’s single thread served reads, commits and landings alike. The proposition is why serving reads of main from a published head cached in stateless compute, as the realization does, leaves their meaning unchanged; what a reader gives up is recency, since the published head is a snapshot at some earlier version. Under a 1,000-writer burst, the reads served from the published head returned correct content in all 1,000 cases in each of six runs, and on an earlier revision with reads served by the authority, 540 of 1,000 succeeded and 460 were refused as overloaded.

6 Agents as concurrent transactions

6.1 Task closures as access sets

The companion paper models a maintenance task \(\tau\) by its necessary edit core \(K_\tau\), its information closure \(I_\tau\supseteq K_\tau\) and its required verification properties \(J_\tau\) [25]. Executed as a change, the task declares a read set \(\mathsf{R}_\tau\) and a write set \(\mathsf{W}_\tau\). The transactional view gives the two descriptions one meaning: the closure is what the task’s correctness depends on, and the declared sets are what the authority can protect. Identify each semantic unit with the location of its source text in Part I’s location tree. Say that \(\mathsf{R}_\tau\) covers \(I_\tau\) when every location of \(I_\tau\) lies in \(\mathrm{sub}(x)\) for some \(x\in\mathsf{R}_\tau\), the descendants of \(x\) in the location tree (Part I, Lemma 4.5).

Proposition 6.1 (Closure coverage). Under the hypotheses of Theorem 4.2, let a task’s change land on \(r\) with base \(b\) at version \(v\), validated as FastForward, Rebase or Merge, with a declared read set that covers its information closure \(I_\tau\). Then every location of \(I_\tau\) has the same content at \(b\) and immediately before \(v\): everything the task depended on was current when it landed.

Proof. Part 1 of Part I, Theorem 6.4 gives \(\tau(S_{b}(r))\equiv_{\mathsf{R}_\tau}\tau(S_{v-1}(r))\), and it holds for every landing that validation did not refuse, including Merge. Agreement on \(\mathsf{R}_\tau\) is agreement on every file and symbol location in \(\bigcup_{x\in\mathsf{R}_\tau}\mathrm{sub}(x)\) (Part I, Section 4.2), which contains \(I_\tau\) by coverage. ◻

Coverage limits which outcomes can occur. When the task’s edits lie within \(I_\tau\), as edits confined to the edit core \(K_\tau\subseteq I_\tau\) do, a read set that covers \(I_\tau\) at path granularity covers every file the task writes; any later write to one of those files then meets \(\mathsf{R}_\tau\), and validation returns Conflict, not Merge. Under coverage, a Merge outcome arises only when reads and refined writes are tracked at symbol granularity and a later change edited a different symbol of a file the task also edits; that is why Assumption 6.2 is among the hypotheses. The write set needs no such discipline: it is the set of touched paths, which contains every path the change edits (Part I, Definition 4.2). Coverage of the read side is sufficient, and without it the guarantee can fail: in Part I’s Example 6.6, two changes each read two files, declare neither, and land side by side although each depended on the file the other wrote. The proposition therefore turns the companion paper’s caution that independence “is only as good as the declared sets” [25] into a checkable condition. An agent that reports retrieval receipts, the fragments it read, can declare them as \(\mathsf{R}_\tau\); a planner that adds referenced symbols to a chosen depth enlarges \(\mathsf{R}_\tau\) toward \(I_\tau\) (Part II, Section 10). Two gaps remain that no declaration closes. Semantic dependencies that cross files without a lexical reference are outside any location tree, and a clean line merge can still be semantically wrong. Both are why the platform runs the policy’s checks on every merged result after it lands and proposes a revert commit when one fails (Part I, Definition 7.5), which is the companion paper’s requirement that independent textual patches still receive combined acceptance.

6.3 Predictions and studies

The companion paper derives predictions P1 to P9 and specifies Studies A to D. The platform makes two predictions testable. P2 says that the benefit of physical file splitting should shrink when coarse files offer equally precise symbol-level retrieval and editing; the platform provides symbol reads and edits by handle. P9 says that dependency-aware scheduling should reduce makespan and integration failures relative to file-disjoint scheduling; the platform provides declared read sets, validation and a planner. Only the following has been measured.

In the first real-model arms of Study A, with 2 to 6 tasks per arm on a deterministic synthetic codebase and one model per provider, closure recall was 1.00 in every arm and exposure precision ranged from 0.08 to 0.43. These samples cannot test P2, and we report them only because they exist. In a two-item scripted P9 case, run once with each of two model providers with identical outcomes, file-disjoint scheduling produced a combination that failed the combined check, with 0 of 2 items accepted. Declaring read sets produced one conflict at landing and a third attempt, with 2 of 2 accepted; scheduling by the planner’s stages accepted 2 of 2 in two attempts with no conflict. This is one scripted case and not a makespan measurement. Predictions P1 and P3 to P8, Studies B and C, and the fault-injection arms of Study D have no results and belong to the planned evaluation (Section 10).

7 Evidence

7.1 Setting

All hosted measurements come from the Cloudflare realization, on an isolated deployment with its own object store, queues and Git namespace, on one account. Two clients drove the benchmarks: a live benchmark on one developer machine, whose latencies include that machine’s network path, and a fan-out benchmark run from a client Worker placed in one AWS region, which can drive 1,000 writers. Latencies from the two clients are not comparable as if they came from one client. Each writer commits one new file on main and then lands it, so the workload has no conflicting writes, no same-file merges and no declared reads. The benchmarks do not record whether the deployed tree was clean, and their outputs are uncommitted files copied into the project’s evidence (Part III, Section 11). Percentiles are over the successful requests of one run, and where several runs exist we report their range.

7.2 Correctness evidence

The model is tied to the code by file-and-commit tables in each Part. The platform’s object identifiers reproduce identifiers computed by Git for blobs, trees and commits, and, according to the commit message that reports it, a clone of the projected repository returned the landed commit and its content and passed git fsck (Part I, Section 10). The platform’s three-way merge agreed with git merge-file on 300 of 300 randomly generated merges, both on whether the merge was clean and on its result. In a local test of the no-lost-update property, 100 of 100 concurrent writers committed and landed on one branch, a figure reported in a commit message without surviving raw output. Part II’s partition-reuse test builds 3, 1 and 0 segments for a first query, a query after a one-directory change and a query pinned at the earlier version, and checks the results (Part II, Section 14).

7.3 The early commit path

The first hosted results were negative. In the early revisions, every commit made several sequential calls to the authority and wrote its objects to the object store and the Git projection before it was acknowledged, and across four runs with 100 concurrent writers commit p95 was between 2.8 s and 3.7 s, against a design target of 1 s. Per-phase timings attribute the miss to an unloaded commit path of 1.5 to 1.6 s at the median, of which the object-store write took 892 ms at the median in one run, and to queueing at the authority under the burst (Part III, Section 5).

Taking the object-store write and the Git push off the acknowledged path brought commit p95 under 1 s. With 100 writers, 28 of 39 runs on revisions from 6dac346 to 4407515 met the target, over a full range of 437 to 2,356 ms; the four runs at 4407515 had 437 to 753 ms, and the two at 03821e0 had 638 and 805 ms. With 1,000 writers on 03821e0, commit p95 was 2,643 ms in a single run in which landings overlapped the commits.

The sub-second result measures a weaker event than the early one. From 734c8a9 on, a commit is acknowledged once the authority or a commit shard, both durable, holds its objects; R2 and Artifacts receive their copies afterwards. That follows the architecture, in which the Git copy is a background projection, but the early revisions acknowledged a commit only after both copies existed. The benchmarks also do not record whether the deployed tree was clean.

7.4 Landing under bursts

Landing paths that built Git trees and merge commits inside the landing could not absorb a burst of 1,000 writers, whether waiting landings polled the authority or waited on a combiner. With polling landers at a1766af, only 20 to 306 of 1,000 landed, and in one run 980 were refused as overloaded. With the combiner at 03821e0, 990 writers committed, 10 commits having failed when the bench client answered with an error, and of those 288 landed, 547 were refused as overloaded and 155 timed out.

The combiner was also slower at 100 writers. Its landing p95 was 25.7 to 30.1 s in two runs from the cloud client, against 3.65 s in the only polling run from that client, which survives in a session transcript on a revision inferred as a1766af; from the developer machine, polling at 4407515 gave 4.2 to 5.4 s in four runs. Two of the combiner’s alarm steps took 10.5 s and 12.5 s. The developers attribute the long steps to reading each fresh tree and blob serially through several storage layers, which is a reading of the code path, not a measurement.

7.6 Batched landing

The landing redesign is merged into the development branch at fef94e7. It submits every waiting landing on a branch to the authority in one call of up to 256 landings, appends path-disjoint landings as changesets, queues landings on the same files for the merge path, defers a member whose reads or writes meet an earlier member’s writes, records commits in 64 commit shards, and serves reads of main from the published head. In each of six 1,000-writer runs on one deploy of that revision, all 1,000 changes landed, no commit or landing was refused as overloaded, and all 1,000 reads returned the correct content.

The results depend on whether each writer has its own token or all writers share one login. With separate tokens, commit p95 was 714 to 1,673 ms, under 1 s in two of three runs, and landing p95 was 1.21 to 1.87 s. With one shared login, commit p95 was 1,140 to 1,614 ms, missing 1 s in all three runs, and landing p95 was 2.17 to 3.03 s. At 100 writers the two runs had commit p95 of 263 and 328 ms and landing p95 of 956 and 568 ms, which meets the developers’ 100-writer target of 100 of 100 landed with landing p95 of at most 2 s. The Git commit of main arrived 3.2 to 5.4 s after landing at p95 at 1,000 writers, down from 17.3 s on the earlier deploy. The burst-span landing rate was 404 to 491 per second with separate tokens and 235 to 284 with one login, over bursts that lasted 2.7 s and 4.3 s end to end in the runs that recorded it. Only the third run of each set kept its full output; the first two survive as summary lines printed from their output before it was overwritten.

These results confirm the direction of Proposition 5.2 on one deploy and one client. They do not establish a sustained landing rate, which no run has measured, and they do not exercise the within-batch write-skew check, because every writer writes its own file and declares no reads.

7.7 Defects found by the analysis

The proofs found three gaps between the implementation and the model, and the analysis of derived data found a fourth.

Batch write skew was found by proof, not by test. At cfa4845 and 03821e0, the combiner validates batch members against the log and not against each other, so two members that each read what the other wrote can land in one entry (Theorem 4.4). Revision c4c8f47 added the check of Part I, Proposition 7.4 to the combiner and to batch verification, and the batch path merged at fef94e7 calls it for every member and defers a member that fails (Appendix A). The check has not been exercised by any hosted run.

Writer-supplied parents were not checked against the base version, which leaves exposed a base strictly between the parent’s version and the head (Part I, Section 6.1). The changeset route checks it, because a commit takes that route only if its single parent is the projected head at its base (Part I, Section 8), and the route is on the development branch from fef94e7. Checkpoints are trusted on their digest alone, and that gap is open.

The search view is not consistent at every snapshot. Its key is the bare subtree identifier, while its segments record full paths, so a renamed directory reuses a segment that names the old paths, and two identical top-level directories share one segment that names only one of them (Part II, Proposition 7.1). The consequences reach access control: grant filtering uses the stored paths, so a caller can receive matches from files under a directory its grant does not cover (Part II, Section 7). A test executed against the crates at cfa4845 confirms the key collision; the effects on search responses were traced through the adapter and not run (Part II, Appendix B). Part II proves two repairs, of which relative paths with a prefixing reduce keeps reuse across renames and forks.

7.8 The model against the measurements

Part III’s capacity model is the one place where the series projects beyond what was measured, and every projected figure below is labelled as such. Using parameters taken from local and per-phase timings rather than from the tails themselves, the burst predictor reproduces the commit p95 of the four early 100-writer runs within 18 percent (Part III, Section 7). The model projected that configurations whose waiting landings poll the single-threaded authority collapse first, and on the controlled deploy the polling mode did fail first; it was wrong about the form of the failure, since the platform refuses requests that queue too long rather than letting waits grow (Part III, Section 8.4). Its projected ceiling for the non-polling combiner, about 11 landings per second, bounds the measured burst rates of 7.0 and 5.9 per second at 100 and 1,000 writers (Part III, Section 8.4). The batch-capacity relation bounds the redesign’s measured rates, as Proposition 5.3 requires. The projections describe a steady state that no run reached, and none of them is a measurement.

8 Relation to Scion

Scion and this series make the same structural move, and their evidence is not comparable. Scion’s published design reports more than 30,000 merges per day, an average of about 0.35 per second, and no landing latency under bursts [2]. The runs reported here are bursts of 100 to 1,000 landings on one branch of one repository within seconds. We make no claim that the system studied here is faster or slower than Scion, and no claim about its behavior under Scion’s workload.

The designs differ in three places, each with a measured consequence (Part III, Section 10). Scion moves a ref by a compare-and-swap on one Spanner row; this architecture places every ref, the log and, in the measured revisions, commit authorization behind one authority per repository, so serialization is per repository and one hot repository is the unit of capacity. That is a choice of key for the authority, not a property of the primitive. Scion’s changesets need no tree objects; the measured revisions built Git trees until changeset landing moved them into a projection. And this platform gates landing on approvals and required checks, where Scion’s published design lands without a global merge lock and tests after merge. The Scion post credits Mononoke, the server of Meta’s Sapling, with pioneering many of its techniques, in particular the Bonsai data model of flat file changes [2, 30].

9 Related work

The transactional table is the template. Delta Lake’s paper gives the log, the checkpoints, the put-if-absent commit and the argument that writes are serializable in record order [3]; its protocol fixes the naming, the replay rule, the version checksum and the ratification contract of catalog-managed tables [14]; and its implementation states the conflict checks and isolation levels that the paper leaves open [11, 13, 12]. Iceberg reaches the same guarantees by an atomic swap of a metadata pointer and makes the isolation level a property of what each writer validates [21]. The series takes this structure intact and changes three things: the atomic step is a command of a serialized authority, read sets are declared at path or symbol granularity, and overlapping writes to one file are merged.

Optimistic concurrency control begins with Kung and Robinson, whose serial validation is the landing step [23]. The serializability theorem, the treatment of granularity and the certifiers come from Bernstein, Hadzilacos and Goodman [5]. The isolation vocabulary is that of Berenson and colleagues [4] and of Adya, whose graph phenomena classify the batch anomaly [1], and Fekete and colleagues characterize when snapshot isolation fails to be serializable [17]. What source control adds is the write-write case: a change to a file is a patch, and two patches to different regions can both apply, with the caveat that the intuition behind clean diff3 merges is false in its obvious formulations [22].

Incremental view maintenance updates a materialized view after its base data change, on the heuristic that only part of a view changes [20], and DBSP turns queries into incremental programs whose linear parts cost in proportion to the change [6]. Build systems memoize task results under hashes of their inputs and are correct only when the hash covers every input and the task is deterministic [29]. Part II’s key sufficiency is that requirement for partitioned derived data, and the search key defect is the classic build error of a task reading an input, its own location, that its key omits. Mononoke separates core data from derived data computed afterwards and derives each changeset’s value from its parents’ [31]; content addressing by Git tree reuses more for content-local kinds and leaves history-dependent kinds keyed by commit.

Among source-control systems, Scion is closest in intent [2], Mononoke’s pushrebase is the nearest precedent for landing on the server [32], and Google’s Piper is the long-standing example of one very large repository with a server-side source of truth [33]. The series differs from these in keeping Git’s objects and identifiers, so every exposed commit can be fetched and verified by stock Git, and in validating declared read sets rather than file overlap alone.

10 Open problems

The foundation leaves seven questions open, each tied to a measurement or a proof that does not yet exist.

10.0.0.1 Sustained landing rate.

Every 1,000-writer result is a burst of a few seconds, and its rate is an average over the burst span (Section 7.6). The developers’ target of 1,000 of 1,000 landed at a sustained 50 per second has not been tested. Part III plans open-loop arrivals at fixed rates from 50 to 800 landings per second for at least ten minutes each, logging every batch call, so that the batch-capacity relation is tested directly and the highest rate held without refusals locates the knee (Part III, Section 9).

10.0.0.2 Authority reads under a burst.

Reads survive the burst because they avoid the authority (Proposition 5.4). With reads served by the authority on an earlier revision, 460 of 1,000 were refused. A read that needs the authority’s current state, rather than a published snapshot, still competes with commits and landings for one thread. The planned run repeats the burst with each read source and counts a refused read as a failed run.

10.0.0.3 Commit p95 under a shared login.

With one shared login, commit p95 missed 1 s in all three 1,000-writer runs, and the shared login’s authorization phase took 381 ms at the median in the run that kept its detail. Whether the shared session’s checks account for the difference is untested.

10.0.0.4 Write skew within a batch.

The check that removes batch write skew is in the merged code and has never run on a workload that could trigger it. A workload whose writers read files that other members of the same batch write would measure how often members are deferred and what deferral costs.

10.0.0.5 Git delay.

Main’s Git commit trails the log by 3.2 to 5.4 s at p95 under a burst. No run measures the delay under sustained load, and no bound on it has been proved; Theorem 5.1 guarantees consistency at a snapshot, not freshness.

10.0.0.6 Checkpoint validation.

A checkpoint whose ref map was altered while its digest was kept is detected only when the altered ref is touched again. A digest of the ref map stored with each checkpoint and in the next entry, the counterpart of Delta’s version checksum [14], would close the gap; it is not built and no test exercises it.

10.0.0.7 Planned evaluation.

Part III’s Section 9 is the planned evaluation for the whole series. Beyond the items above, it measures the authority’s service time per call type by saturation, the land combiner’s batch sizes and cycle times, push sizes, per-tier hit rates under cold reads, and the costs that Part II lacks: segment build time and size, the fraction of partitions that change per landing on real repositories, and the delay from landing to a queryable segment. It also runs the companion paper’s Study A and P9 at a size that can test them, with closure recall, exposure precision and cost per accepted change as metrics [25]. Each item names the outcome that would refute its expectation.

Two further limits are structural. Serializability holds per ref, like Delta’s per-table limit, and nothing in the model gives atomicity across refs or repositories [3]. And log compaction and retention are not designed, which matters because the authority’s database is bounded and a repository at Scion’s merge rate would add tens of thousands of entries per day (Part III, Section 4).

11 Threats to validity

The theorems are proved about a model, and the model’s correspondence with the code was established by reading the code at pinned commits, not by mechanized verification. The interleavings of landing, claiming and leasing were tested by example, not explored exhaustively, and a model-checked test of them is the strongest missing piece of correctness evidence (Part I, Section 12).

The performance evidence comes from one account, two client locations and few runs per revision. The early group’s run-to-run spread of commit p95 was 0.93 s across four runs, so no single run should be read as precise. The deployed tree’s cleanliness was never recorded, the outputs of the later runs exist only as uncommitted files, and for the fef94e7 runs the bench client carried an uncommitted change that reports commits per shard. The workload is synthetic: one tiny new file per writer, with no conflicting writes and no declared reads, so it exercises the disjoint fast path and nothing else.

The acceptance point moved during the series. The sub-second commit results count a commit as accepted once a Durable Object holds its objects, the early results once the object store and the Git projection did. The two groups do not measure the same event, and the paper never compares them as if they did.

The capacity projections rest on assumptions that no run has tested at sustained saturation: uniform cost per authority call, a closed population with fixed think time, and a combiner cycle independent of batch size (Part III, Section 11). They are labelled as projections wherever they appear.

12 Conclusion

A repository can be run as a transactional database, and the guarantees of transactional tables carry over with proofs: deterministic replay, immutable snapshots, and landings serializable in log order relative to what they declare they read, whenever no line-level merge is needed. Derived data become views that are guaranteed consistent at a snapshot exactly when their keys determine their stored results, and Git becomes one of those views. The composition is the practical result. Because every guarantee is stated over log entries and the Git commit of a branch is a deterministic function of the log, Git objects can leave the landing path, and the authority’s work per landing shrinks to a validation query and an append, batched. The measurements follow the theory on one realization: landings that built Git while landing failed under a burst of 1,000 writers, and batched changesets landed every writer in every run.

What the foundation enables is a source-control system whose correctness rests on a transaction log and whose cost can be stated per primitive before it is built on a particular cloud. It also gives the companion paper’s conditions a precise meaning at landing: independence is exactly order-insensitive landing without merge, and a task’s information closure is protected wherever its declared read set covers it. What remains open is quantitative and empirical: a sustained landing rate, reads that need the authority under load, commits under a shared login, the Git delay, and a workload that exercises write skew within a batch.
