1 Introduction

Source code and source control can now be treated as transactional abstractions. A repository is a database, a change is a transaction with a read set and a write set, landing is a commit under optimistic concurrency, a version is a snapshot, and derived data are views kept consistent with a snapshot. This series lays foundations for that view. This Part supplies the systems layer: it builds the transaction system on cloud-portable primitives and asks what its serialized authority costs and where it saturates.

We argue that the next evolution in code is transactional, and that data went through the same change first. Data lakes began as files on object stores; concurrent writers and derived computation broke file-level semantics, and the field moved to tables with a transaction log, snapshots and optimistic concurrency [1], with partitioned computation over those snapshots [2]. Source control is now under the same pressure. Coding agents are always online, they write small changes against a head that moves while they work, and there can be thousands of them per repository. Anthropic’s account of Scion reports that merges per day grew from about 2,500 in May 2026 to more than 30,000 in September 2026, and that source control became the largest bottleneck in development [3]. Scion’s published design separates commit creation from ref updates, lands changesets through a write-ahead log, and keeps a ref compare-and-swap on one database row [3], which is the move data made. This Part supplies one piece of evidence for the argument: what such a transaction system costs on cloud primitives, measured on one realization.

Part I of this series [4] formalizes a design in the same family as a Delta-style transaction log over Git-compatible objects [1]: a hash-chained log of ref moves, checkpoints, snapshot reads pinned to a log version, and landing by backward validation against declared read and write sets [5]. Part II [6] treats blame, search, symbols and codemods as partitioned jobs over immutable snapshots. Both Parts state their results over abstract primitives, and neither says what the design costs in a deployment. This Part states the primitives’ contracts, maps them onto Cloudflare’s serverless products as the reference realization, separates the limits of those products from the limits of the architecture, reports what was measured, and builds a queueing model over primitive service times that extrapolates the measurements to larger fleets of agents.

The author designed and built the system under study, YonedaRepo; terms such as “authority”, “push queue” and “land combiner” are this project’s names, not industry usage. The implementation is in Rust (compiled to WebAssembly) with a thin TypeScript adapter, and every claim about it in this paper is tied to a file and commit of its repository in Appendix A [7].

The principal result is measured. The landing redesign, merged into the development branch (fef94e7, merge f9d9c14), appends path-disjoint changesets to the log in one authority call per batch of up to 256 landings and builds main’s Git objects in the background. In each of six bursts of 1,000 writers on one repository it landed all 1,000 changes, refused no commit, landing or read, and kept landing p95 between 1.21 s and 3.03 s. Commit p95 was under 1 s in two of the three runs in which each writer had its own token, and in none of the three in which writers shared one login. On an earlier controlled deploy, the two landing modes that built Git trees and merge commits on the landing path landed 4 and 385 of 1,000 changes under the same burst, the first refused as overloaded and the second timed out. The redesign has costs and gaps: main’s Git commit arrived 3.2 to 5.4 s after landing at p95, reads succeed only because they are served from a cached head rather than the authority, and the measured landing rates are averages over bursts of a few seconds, not sustained rates.

The path to that result includes a negative one. In the early revisions, commit acceptance p95 was between 2.8 s and 3.7 s across four runs with 100 concurrent writers, against a design target of 1 s. Per-phase timings attribute the miss to an unloaded commit path of about 1.5 s, more than half of it an R2 write, and to queueing under the burst at the serialized authority, a Durable Object in this realization. Later committed revisions took those costs off the acknowledged path, and in 28 of 39 runs commit p95 was then under 1 s, with a weaker meaning of acceptance.

The second result is a capacity model over the primitives’ service times. It reproduces the early 100-writer commit tails within 18 percent, using parameters taken from local and per-phase timings rather than from the tails themselves. It projects that the land combiner’s cycle sets each branch’s ceiling, and that configurations in which waiting landings poll the single-threaded authority collapse past that point. The controlled runs confirmed the second projection in direction, and showed that the realization refuses requests rather than letting them queue; the measured batch call of the redesign bounds its landing rate as the model’s batch-capacity relation says it should. Section 8 sets each projection next to the measurement that tests it.

2 System model

A repository in this series has four components: immutable objects, workspace changesets (commits that no protected ref points at yet), protected refs, and stateless compute [4]. The protected refs are governed by a hash-chained transaction log. Each log entry moves one ref and records the paths the change touched; the snapshot at version vvv is the ref map that replaying the first vvv entries produces; and checkpoints let a reader start a replay part way. A writer lands a change by submitting a proposal P=(r,b,o,W,R)P = (r, b, o, W, R)P=(r,b,o,W,R): a ref, the base version it read, the ref’s expected old value, and declared write and read sets. The authority validates the proposal backwards against every entry since bbb and answers fast-forward, rebase, merge or conflict. It then applies the result as one atomic append that moves the ref and writes the entry in a single transaction. Part I defines these objects (its Definitions 4.6 to 4.16) and proves their properties; this Part uses them without change.

The land combiner is the part of Part I’s design that this Part measures most closely (Part I, Definition 7.1). It queues landings per branch, lets one Worker at a time hold a lease with an epoch, builds one octopus merge commit for a batch B=(t1,…,tk)B = (t_1, \dots, t_k)B=(t1​,…,tk​) of at most 64 queued changes (128 from revision 03821e0), and lands the batch as one log entry. Part I proves that the combiner preserves the single-writer discipline of the append (its Theorem 7.2) and that members of one batch can exhibit write skew with each other (its Theorem 7.3). The batch size therefore has a semantic cost as well as the latency cost studied here.

Three of Part I’s invariants (its Table 3) matter on this platform. I4 says that a ref move, its log entry, the projection target, any checkpoint and the landing record commit in one transaction with no network input or output. I6 says that a commit is recorded only after the object store’s readback matches what the authority built, and that a hidden ref keeps it reachable. I13 says that branch refs in the object store follow the authority, are never forced, and report a refused update as drift.

Derived data enter this Part only through their deployment. Part II defines a job as a snapshot, a partitioning, a task kind and a policy, and shows that values keyed by content need recomputation only for changed partitions (its Definition 3.3 and Theorem 5.3) [6]. Here derive jobs run from a queue after landing, their segments are stored in R2, and the commit path waits for one derivation step whose cost appears in Table 3.

Two further facts from the companion paper frame the capacity question [8]. Its independence condition (its Eq. 1) decides which work items may run in parallel, and its critical-path bound (its Eq. 2) says that a set of work items needs at least the larger of total work divided by the number of workers and the longest dependent chain. A mandatory serial resource is a chain that every operation passes through. The capacity model of Section 6 is a quantitative version of that observation for the serial resources of one repository.

3 Primitives and the reference realization

The architecture is defined over six primitives, and only their contracts enter Parts I and II. Table 1 states each contract, the Cloudflare product that realizes it in YonedaRepo, the limit of that product that binds the design, and one other product whose documentation offers the same contract. The table makes no performance claim about the other products. Scion’s ref update, a compare-and-swap on one Spanner row, is evidence that the serialized-authority primitive is available on another cloud [3, 9]. Every measurement in this paper comes from the Cloudflare realization, on an isolated deployment with its own Artifacts namespace, R2 bucket, D1 database and queues, so no measurement shares state with any other workload.

3.1 The serialized authority

The serialized authority must hold durable state per key and execute a compare-and-set on a ref together with a log append, linearizably. In the reference realization each repository has exactly one Durable Object of class SourceRepository, addressed by the repository’s name. It holds the transaction log, the refs table, checkpoints every 64 versions, the commit records, the landing queue and lease, approvals, check runs and access grants, all in its SQLite database. A Durable Object is single-threaded and its storage is co-located with its code [25]. SQLite writes inside it are synchronous, a transaction is all-or-nothing, and an output gate holds a response until the write it depends on is durable [26]. Cloudflare’s description of the storage layer states that a write is confirmed once at least three of five followers acknowledge it [27]. These properties give Part I’s atomic append its meaning on this platform: the compare-and-swap on a ref, the log entry and the landing record are one SQLite transaction, and no other request to the repository can observe a state between them.

From 5bac6b3 on, commit records leave the authority: each commit is recorded with its staged objects in one of 16 commit-shard Durable Objects chosen by the commit’s identifier (64 from fef94e7), and the authority adopts a commit the first time an operation needs it. This is the per-workspace direction of the design notes, realized with shards keyed by commit rather than by workspace.

The price of the design is that the authority remains a serial resource for its whole repository. A Spanner row in Scion holds one ref [3, 9]; the authority here holds every ref, every commit record and every landing of the repository. Requests to two branches of one repository queue behind each other, while requests to two repositories do not interact. The architecture needs a total order only for each repository’s log; that commit preparation and reads share the same single thread is a property of this realization.

3.2 The object store and the Git projection

The object-store primitive needs only immutable puts and gets keyed by content. Objects are real Git blobs, trees and commits whose identifiers are the SHA-1 of the type, length and content [28]. In the early revisions measured here, Artifacts is both the Git projection and the authoritative object store. Its Workers binding exposes reads of commits, trees and blobs and the minting of tokens, but no object write or ref compare-and-swap, so the platform writes objects by speaking Git’s receive-pack protocol over HTTP [11, 23]. Every recorded commit is kept reachable by a hidden ref named after the commit, and branch refs in Artifacts follow the authority through an outbox with an expected old value, which is Part I’s invariant I13. People clone the Artifacts repository read-only with a short-lived token; agents never clone.

The architecture treats the Git projection as optional and asynchronous. The early revisions measured here did not: every commit was pushed to Artifacts and read back before it was acknowledged. Later revisions made R2 the store of record, with a projector that drains staged objects to R2 and pushes only protected refs to Artifacts. The distinction matters for capacity because it decides whether a push is on the path that acknowledges a commit.

3.3 Read tiers

Reads of immutable objects pass through three tiers: the Cache API at the serving location, then R2, then the authoritative store. Each tier asks only the next one, a miss fills the tiers above it, and keys carry the repository so that cached bytes are reachable only through that repository’s authorization. Because an object never changes, no tier needs invalidation; ref values are never part of an object cache key. This is the same structure as Scion’s daemon, cache and server tiers [3], with two differences. There is no per-machine daemon tier in the platform, and the edge tier is per location, so a miss at one location does not fill another.

3.4 Asynchronous and heavy work

Work that need not finish before a response goes to the durable queue: deriving search segments and symbols after a landing, projecting branch refs to Artifacts, and dispatching check runs. None of it is on the commit or landing path, so the queue’s limits do not enter the capacity model. The same holds for imports, which run as Workflows.

Checks are the exception that matters. They run on container compute, Containers in this realization, on the exact commit under test, and a landing cannot proceed until its required checks pass. A run on a commit near a branch head starts from a warm-start seed in R2 and fetches only the blobs that differ, which is the platform’s counterpart of Scion’s daemon starting from a refreshed snapshot [3].

3.5 Request paths and serialization points

Definition 3.1 (Serialization point). A serialization point is a resource that serves at most one operation at a time for a given key, such as a repository or a branch. Its service time sss is the time for which one operation holds the resource. A serialization point that serves a batch of mmm operations in one service is a batch serialization point with service time T(m)T(m)T(m).

Definition 3.2 (Commit path and land path). A commit request in the early revisions reads the repository’s status for authorization (two or three reads per request in the measured runs) and runs five stages in order: (1) it reads a snapshot of the target ref from the authority and answers the authority’s requests for the trees on changed paths in one or more prepare calls; (2) it starts writing the new objects to R2 and the edge cache, and at the same time pushes a single-ref receive-pack through the push queue; (3) once both have finished, it reads the commit back from Artifacts; (4) it records the commit at the authority and dispatches check runs; and (5) it classifies review classes and derives symbol writes in parallel, recording the review classes at the authority, and the symbol writes too when the changed files contain symbols. A land request first attempts a direct compare-and-swap at the authority. If the branch needs a merge, it enqueues the change and then polls its landing’s status and the branch’s lease until a batch lands it; a request whose claim on the lease succeeds builds and lands the next batch itself.

The later revisions shorten both paths. A commit makes one authority call, which authorizes it and names its parent, is built in the Worker, and is acknowledged once its commit shard holds it. A landing adopts the commit into the authority and lands or enqueues it. At 4407515 a waiting landing polls the lease with back-off; at 03821e0 it waits on the land combiner instead.

In the early revisions, the measured sequential commits made ten round trips to the authority in an idle repository: four prepare calls, three status reads, one snapshot, one record and one review-class record. The burst’s commits made seven, because they add a file one directory below the root and need one tree round where the sequential edits need three; the extra status read of the sequential commits is unexplained. The text files of the benchmark contain no symbols, so no symbol-write call appears in either case. The visits of one commit to the authority are sequential.

Four serialization points lie on these paths: the repository authority, keyed by repository; the push queue together with Artifacts’ receive-pack, keyed by Artifacts repository; the land combiner’s lease, keyed by branch; and any R2 key written more than once per second. In the later revisions the push queue leaves the commit path, and the 16 commit shards add a serialization point keyed by shard. Everything else on the paths is stateless or partitioned by object: Workers isolates, the compute that builds trees and merges, R2 writes to distinct keys, and edge cache writes.

4 Realization limits

Every limit in this section belongs to a product of the reference realization, not to a primitive. Each subsection names the primitive property involved and what another realization would change.

4.1 The single-threaded authority

Cloudflare documents a soft limit of about 1,000 requests per second for one Durable Object, and advises that complex operations with storage writes sustain 200 to 500 requests per second [13, 14]. The authority executes each command atomically and serially (Part I, Assumption 4.14), and its landing transaction does no network input or output (invariant I4), so its service time is local computation and SQLite work. The service time is not measured inside the object on the hosted platform: the Server-Timing instrumentation measures waits in the Worker, and Workers clocks advance only across input and output, so a Durable Object call appears as the round trip including network and queueing. Section 6 therefore estimates the service time indirectly.

The primitive asks only for linearizable compare-and-set per key. A single thread per repository is one way to provide it, and it makes the whole repository one key. A realization with one row per ref, as in Scion, would serialize ref moves per ref instead, but the log of Part I still needs a total order per repository, so such a realization would need one log per branch or a separate sequencer. This paper analyzes neither.

A second limit is storage. An object’s SQLite database is limited to 10 GB on the paid plan [13], and the log has no retention or compaction protocol yet. The log of a repository with Scion’s merge rate would grow by tens of thousands of entries per day, so log compaction is a precondition for long-lived repositories on this design, independent of throughput.

4.2 The receive-pack limit

The first hosted test with 100 concurrent commits failed 91 of them with the Artifacts error ERR artifacts_git_receive_pack_busy. Artifacts accepts one receive-pack per repository at a time. This limit does not appear in the documentation pages consulted; it is consistent with Cloudflare’s statement that each Artifacts repository is its own Durable Object [29]. The constraint belongs to Artifacts as the Git projection, not to the architecture. The object-store primitive accepts concurrent puts of distinct keys, and with the projection made asynchronous, as the architecture allows, no push would lie on the commit path. In the early revisions the projection was authoritative, and the platform’s response was a push queue.

Definition 4.1 (Push queue). The push queue of an Artifacts repository is a Durable Object that holds the single-ref receive-pack bodies waiting to be sent. While one combined request is in flight, new bodies wait. When it completes, the queue takes the oldest waiting bodies, at most one per ref, up to mmax⁡=64m_{\max} = 64mmax​=64 bodies and 24 MiB, combines them into one receive-pack whose pack holds the union of their objects and whose commands are their single commands, sends it, and splits Git’s report so that each caller receives the status of its own ref. A busy answer is retried up to six times.

After the queue was added, 50 of 50 concurrent commits succeeded, and the 100-writer runs of Section 5 carried 47 to 63 commits in one combined receive-pack. The correctness of combining rests on two properties of the Git protocol and of the platform’s pushes.

Proposition 4.2 (Combined push is equivalent to separate pushes). Let p1,…,pmp_1, \dots, p_mp1​,…,pm​ be single-ref receive-pack requests with pairwise distinct refs r1,…,rmr_1, \dots, r_mr1​,…,rm​, each of whose packs contains every object reachable from its new value that the repository lacks. Suppose the server applies the commands of a receive-pack without the atomic capability independently, deciding each command from its ref’s old value, its new value and the presence of the new value’s objects, with no hook or quota that couples one ref’s update to another’s. If the combined request is unpacked successfully, the status reported for rir_iri​ equals the status that pip_ipi​ would receive if sent alone against the same ref state, for every iii.

Proof. The combined pack contains every object of every pip_ipi​, deduplicated by identifier. Identifiers are content hashes, so deduplication removes only byte-identical objects, and every object that pip_ipi​ needs, which by hypothesis its own pack supplies, is present. The extra objects of other requests can only add to what the repository holds, and the hypothesis already makes pip_ipi​ complete without them. The server’s decision for the command of pip_ipi​ depends on the old value of rir_iri​, the new value, and the presence of the new value’s objects. The refs are distinct, so no other command in the batch changes the old value of rir_iri​, and without the atomic capability the failure of another command does not change the outcome of this one [23]. Each input to the decision is therefore the same as when pip_ipi​ is sent alone. ◻

The hypotheses of a successful unpack and of independent commands both matter: a repository-wide quota such as the 1 GB limit would couple the requests of one batch. A malformed or oversized body in a batch makes the whole batch fail, so combining introduces fate sharing that separate pushes do not have. The platform bounds the damage by refusing duplicate refs, capping the batch at 24 MiB, and letting every caller retry. In the measured workload every push creates a fresh hidden ref with an all-zero old value, so the distinctness hypothesis holds by construction, and the authority builds each pack from every new object of its commit, so the completeness hypothesis holds as well.

The push queue removes the failures but keeps the serialization. A combined receive-pack took 409 to 440 ms to send under the burst and 121 ms for a single commit. The push queue is a batch serialization point in the sense of Definition 3.1, and its capacity is m/T(m)m/T(m)m/T(m) commits per second, which Proposition 6.11 relates to the batch size.

4.3 Object-store write limits

R2 is strongly consistent and limits concurrent writes to one key to one per second [10, 30]. Content-addressed objects have distinct keys, so object writes of different commits do not contend unless two commits write a byte-identical object. Yet in one instrumented 100-writer run, 7 of 100 commits failed with R2 error 10058, “Reduce your concurrent request rate for the same object.” Some key is therefore written by many commits. Reading the committed commit path does not reveal it: every object the commit path writes to R2 is keyed by its content hash, and the burst’s writers produce distinct blobs, trees and commits. The build that ran H4 came from a working tree whose exact contents were not recorded, so the key may lie in uncommitted code. Until it is identified, this limit is a potential ceiling of one commit per second for whatever path writes that key, and the projections of Section 8 assume that the key can be removed from the commit path. The per-key rate and the latency of R2 puts, which Section 5 shows to have dominated an unloaded commit in the early revisions, are properties of this object store. The primitive’s contract says nothing about latency, and another store would have its own, which this paper does not measure.

4.4 Worker connections and subrequests

A Worker invocation keeps at most six outgoing connections open and may make 10,000 subrequests on the paid plan [19]. These are limits of the stateless-compute realization. They do not bind a one-file commit, but they bound bulk operations. Creating a 3,000-file repository took 183 s while every object was written through the R2 and edge tiers, and 6.9 s once large commits wrote only their commit object through; a 10,000-file creation exceeded the subrequest limit before that change and took 11.6 s after it. An earlier change that wrote the cache in bounded chunks rather than all at once cut a 5,000-file import from 129 s to 16 s.

4.5 Other limits

Artifacts limits a repository to 1 GB and a blob to 32 MB [11]. Scion’s main branch history is almost 100 GB [3], so a repository of that size cannot be hosted in one Artifacts repository. That limit of the Git projection, not throughput, is the first obstacle to a Scion-sized monorepo in this realization, and it is one reason later revisions made R2 the store of record. Queues and Workflows have limits far above the rates projected here (Table 1). Containers have no documented cold-start time; Section 5 reports the measured one.

5 Measured evaluation

5.1 Environment and workloads

All hosted measurements use the isolated platform-only Worker on Cloudflare’s paid Workers plan, with real Artifacts, Durable Objects, R2 and Cache API. Two clients drove the benchmarks. The live benchmark ran on one developer machine, so its latencies include that machine’s network path. The fan-out benchmark ran in a client Worker placed in the AWS us-east-1 region, which can drive a thousand writers; it reports client-side latency and the server-side Server-Timing total separately. Latencies from the two clients are not comparable as if they came from one client.

The live benchmark seeds a repository with 100 files, starts 100 writers at once, each of which commits one new file on main and then lands it, and then reads the 100 new blobs concurrently. It then times sequential one-file edits on a small and a large repository and compares a git clone of the Artifacts projection with a first read through the API. The fan-out benchmark runs the same commit-then-land cycle per writer at 20, 100 or 1,000 writers. Percentiles are computed over the successful requests of one run, so a p95 over 100 requests is set by the five slowest. The deployed tree’s cleanliness is not recorded by the hosted benchmarks, so each run is attributed to the revision its output names.

The code changed between runs, and the runs fall into three groups. The early group (H1 to H4) ran revisions from 535d9ab to the Server-Timing instrumentation of ebbee09, in which every commit made seven authority calls under load, wrote its objects to R2 and pushed them to Artifacts before it was acknowledged. From 734c8a9 on, a small commit is acknowledged once a Durable Object holds its objects, and from 5bac6b3 that object is one of 16 commit shards per repository; R2 later became the store of record and Artifacts receives only protected-ref projections. The later group ran these revisions with polling landers, and the last group ran 03821e0, which replaced polling with a land combiner that waiting landings do not poll.

The early group missed the commit target. Commit acceptance p95 was between 2.8 s and 3.7 s across four runs, against a design target of 1 s with 100 concurrent writers, and every commit and landing succeeded only in H1 and H2. H3 lost 9 commits to an input-validation error whose message the run did not keep, and H4 lost 7 to the R2 per-key limit. The benchmark’s inputs are fixed, so the H3 failures arose from server-side state under load rather than from the inputs, but the cause is unknown. The deployed revision of H3 and H4 was not recorded, and the two runs were not repeated for this paper.

The later group met the commit target, with a changed meaning of acceptance. In 28 of 39 runs on twelve committed revisions from 6dac346 to 4407515, commit p95 was under 1 s, ranging from 437 ms to 2,356 ms; every one of the 39 runs committed and landed all 100 writers. On 4407515 all four runs fell between 437 ms and 753 ms client-side, and between 198 ms and 606 ms server-side. An accepted commit in these revisions is durable in a Durable Object, the authority’s staged copy or a commit shard, but not yet in R2 or in Artifacts. That is a different durability point from the early group’s, and Section 11 treats it as such. The outputs of these runs exist as uncommitted files only.

Landing did not improve with the non-polling combiner. At 100 writers from the same us-east-1 client, the polling path landed with p95 3.65 s on the run attributed to a1766af, while the combiner at 03821e0 landed with p95 25.7 to 30.1 s. The run on the polling path survives only as a tool result in a session transcript, and its revision is inferred, so the comparison rests on one run on each side.

At 1,000 writers, both landing paths overloaded the repository authority. 5.3 Batched landing on the development branch, measured

The landing redesign, merged into the development branch (fef94e7, merge f9d9c14), lands a burst of 1,000 writers without refusals. In every one of six 1,000-writer runs on a deploy of fef94e7, whose deployed platform was a clean build of that revision while the bench client carried an uncommitted change that reports commits per shard, all 1,000 changes landed, no commit or landing was refused as overloaded, and all 1,000 reads returned the correct content. The measured mode, configured as batch, submits every waiting landing on a branch to the authority in one call of up to 256 landings. Path-disjoint landings append changesets to the log, landings on the same files are queued for the merge path, and a member whose reads or writes meet an earlier member’s writes waits for the next batch. Commits are recorded in 64 commit shards, between 7 and 30 per shard in these runs, and reads of main are served from the published head that the Worker caches rather than from the authority.

The results depend on whether each writer has its own token or all writers share one login, and Table 2 gives both sets as ranges over three runs each. With separate tokens, commit p95 was 714 to 1,673 ms, under 1 s in two of the three runs, and landing p95 was 1.21 to 1.87 s. With one shared login, commit p95 was 1,140 to 1,614 ms, missing 1 s in all three runs, and landing p95 was 2.17 to 3.03 s; the shared login’s authorization phase alone took 381 ms at the median in the run that kept its detail. At 100 writers both runs met every target, with commit p95 of 263 and 328 ms and landing p95 of 956 and 568 ms.

The rate is a burst rate, and no sustained run exists. Over the span from the first landing request to the last answer, the runs landed 404 to 491 changes per second with separate tokens and 235 to 284 with one login; each burst lasted 2.7 s and 4.3 s end to end in the runs that recorded it. A burst that short says nothing about the rate the authority can hold, which Section 9 plans to measure.

The delay before main’s Git commit exists fell with the redesign but did not vanish. Its p95 was 3.5 to 4.6 s with separate tokens and 3.2 to 5.4 s with one login at 1,000 writers, and 2.7 and 2.4 s at 100 writers. A reader that needs main’s Git commit, such as a person cloning it, waits that long; a reader of the log or of the published head does not.

The reads succeed because they avoid the authority, which is a trade-off rather than a removal of the limit. On an earlier revision of the same branch, the same mode with reads served by the authority returned 540 of 1,000 reads correctly and refused 460 as overloaded, and a changeset mode that also began commits at the authority refused all 1,000 reads. The authority still cannot serve a 1,000-writer burst of commits, landings and reads at once; the design moves the reads elsewhere.

Two qualifications apply to all six runs. Only the third run of each set kept its full output; the first two survive as one-line summaries that the benchmark script printed from their output before overwriting it. The workload writes one new file per writer and declares no reads, so it never exercises the within-batch write-skew check, which fef94e7 contains (Part I, Proposition 7.4).

5.4 Controlled comparison of landing modes

Because fef94e7 removed the older landing modes, the controlled comparison comes from an earlier deploy, dd6c9a8 on branch claude/native-p95e, in which the benchmark chose the landing mode per run on one deploy from one client (runs S1 to S6 in Table 2). In its changeset mode a landing whose paths are disjoint from everything landed on its branch since its base appends its changeset to the log with one indexed query, without building Git objects or a merge commit, and a deterministic projector builds the branch’s Git commit afterwards.

At 1,000 writers on that deploy, the changeset mode landed all 1,000 changes with a landing p95 of 18.7 s and a commit p95 of 1,698 ms, and no commit or landing was refused. On the same deploy the polling mode landed 4 of 1,000, with 994 refused as overloaded and a landing p95 of 104.0 s, and the combiner landed 385 of 1,000, with 615 timeouts and a landing p95 of 64.8 s. At 100 writers the changeset mode landed all 100 with a landing p95 of 1.2 s, against 2.4 s with polling and 13.0 s with the combiner. The landings that built Git trees and merge commits on the landing path failed under the 1,000-writer burst; the landing that appends changesets and builds Git objects in the background did not. That deploy’s changeset mode still had the costs that fef94e7 later reduced: a burst-span rate of 49.7 landings per second, a Git projection delay p95 of 17.3 s, and 422 of 1,000 reads refused as overloaded, which the benchmark’s overload count omits because it covers commits and landings only. The deploy was attributed to dd6c9a8 from the session record; two of the six output files name a later commit because the checkout moved during the runs, and no deploy happened in between.

5.6 Landing under a burst

Landing p95 under the burst ranged from 5.0 s to 7.7 s in the early group, while the direct compare-and-swap call to the authority took 86 to 87 ms at the median. Most of the landing time was waiting on the land combiner. A landing request made 13.6 to 16.0 lease claims and 14.6 to 17.0 status reads on average, summing to 2.5 to 2.6 s and 2.6 to 2.9 s of waiting respectively. Three to four batch landings served each burst of 91 to 100 landings, which puts the mean batch near 25 to 33 changes if every landing went through a batch. The change-log stream recorded the same pattern on later revisions: across 18 repositories with 101 accepted changes each, a 100-landing burst became two to four octopus batches.

The landing request that held the lease spent about 2.4 to 2.6 s on one cycle: building and pushing the octopus merge commit, recording it, and the batch landing call itself (487 to 579 ms). A landing that arrives during a cycle waits for it and then for its own, and a landing in the last of three or four batches waits for more. The measured landing p95 of 5.0 to 7.7 s corresponds to two to three such cycles.

Polling was a property of the adapter’s landing loop in the Worker, not of the combiner’s design, and it dominated the authority’s load: on average an early-group landing made about 30 authority calls, of which 28 were polls. Revision 4407515 folded the status read into the claim and backed off between polls from 20 ms to 320 ms, and a landing then made 6.5 to 8.2 claims on average.

The non-polling combiner at 03821e0 holds waiting landings in memory and lands batches of up to 128 in steps driven by Durable Object alarms. Two of its alarm steps recorded wall times of 10.5 s and 12.5 s during the 20-writer and 1,000-writer runs, and the developers’ message attributes the long steps to reading every fresh tree and blob serially through five storage layers. Only the two wall times are measured; the cause is the developers’ reading of the code path. A step of that length, together with waits that the landing loop renews in rounds of 20 s, is consistent with the measured 100-writer landing p95 of 25.7 to 30.1 s, though that consistency is an inference.

5.8 Local measurements

Local measurements ran in workerd, the open-source Workers runtime, on one developer machine with simulated Durable Object and R2 latency. These figures are not evidence about hosted latency, because the hosted path is dominated by network round trips that workerd does not reproduce.

A separate local benchmark of the earlier agent-layer authority, a different Durable Object class with a different schema, measured 662 commands per second with four concurrent clients on one repository, 676 per second with 32 clients over 8 repositories, and 646 per second with 64 clients over 16 repositories. Throughput did not rise with the number of repositories, so these figures measure the cost of a command to one workerd process rather than a per-object limit. Section 6 uses the four-client figure as an independent estimate of per-call service time.

6 Capacity model

The measurements describe one repository with 100 writers, but the question that motivates the system concerns thousands. The model below is stated over the primitives and parameterized by their service times: the authority’s service time per call sss, the push queue’s send time, the land combiner’s cycle and its batch size kkk. The Cloudflare measurements supply one instantiation, and the model can extrapolate them only after it reproduces the 100-writer runs, which Section 7 checks.

The model uses five results. The first bounds waiting at a work-conserving point when many operations arrive together, which is the situation of the benchmark.

Lemma 6.7 (Burst waiting bound). Let NNN jobs share a work-conserving single server. 8 Projected capacity

Every number in this section, except those labelled measured, is projected, estimated from measured per-operation cost of the Cloudflare realization through the model of Section 6. Another realization would enter the same formulas with its own service times, which this paper does not estimate. The projections describe a steady state in which agents commit and land repeatedly; the measured comparison points are bursts, and Section 8.4 keeps the two apart.

8.1 Workload shape

Scion’s published design reports more than 30,000 merges per day, an average of about 0.35 merges per second [3]. The post reports no peak-to-average ratio, no count of agents, no per-agent rate and no landing latency under bursts. This paper therefore assumes a think time ZZZ of 60 s between an agent’s landing and its next commit, varied from 10 s to 600 s, and makes no claim that its runs or projections are comparable with Scion’s operation.

8.4 Projections against measurements

The side-by-side runs on dd6c9a8 test the model’s qualitative claims, though not its steady-state numbers, because they are bursts of 1,000 writers that all start at once. The model was right that polling fails first. On the same deploy, the polling mode landed 4 of 1,000 changes and the authority refused 994 as overloaded. It was wrong about the form of the failure. Corollary 6.12 describes an unbounded queue whose waits grow without limit; the platform bounds the queue of a Durable Object and refuses requests that wait too long, so saturation appears as refusals rather than as slow answers.

The model was right that the measured combiner cannot reach the rates of the other modes. Its projected ceiling of about 11 landings per second bounds the measured burst rates of 7.0 per second at 100 writers and 5.9 per second at 1,000 writers, where 615 landings timed out after the landing loop’s 120 s deadline. The bound is not tight: a burst spends part of its span before the first batch fills and after the last.

The changeset mode of dd6c9a8 measured 49.7 landings per second over the span of the 1,000-writer burst, with all 1,000 landed. The batch-capacity relation says that 49.7 per second with batches of 128 corresponds to one full batch every 2.58 s, close to the 2.56 s that a rate of 50 per second requires; that deploy logged neither batch sizes nor cycle times, so the relation could not be tested there.

The batched landing of fef94e7 logs both, and it gives the relation its one direct test. Its batches held 256 landings, and the authority call that lands a batch took 308 ms at the median and 372 ms at p95 in the run that kept its detail. By Proposition 6.11 that call bounds one branch at 256/0.372≈690256/0.372 \approx 690256/0.372≈690 to 256/0.308≈830256/0.308 \approx 830256/0.308≈830 landings per second. The relation was right about what limits landing: one serial call per batch, not one per landing. It does not say what rate the branch sustains, because no sustained run exists.

8.5 Commit latency

The commit target is a property of the commit path, not of the landing path. With the early commit path, no configuration is projected to bring commit p95 under 1 s at any fleet size, because the unloaded p95 alone, about 1.5 s, exceeds it. With the sharded commit path of C2 and C3, the unloaded p95 is about 345 ms and queueing at the authority adds little until a polling configuration collapses: one call per commit at 1.51 ms is a small load even at the combiner’s ceiling. In C3 commits stay near 0.35 s at every fleet size in the model, with the acceptance semantics of the later revisions. Measured bursts are slower, because landings and reads overlap the commits: at 1,000 writers on fef94e7, commit p95 was 714 to 1,673 ms with separate tokens and 1,140 to 1,614 ms with one login, under 1 s in two of six runs.

8.6 Scale against the Scion workload

The tests are not comparable with Scion’s operation: Scion’s published design reports a daily average and no burst latency, while these figures are a measured burst-span rate and projected steady-state ceilings for one branch of one repository. With that caveat, the projected ceilings of 11 to 24.6 landings per second are 30 to 70 times the published daily average, and the measured burst-span rates of 235 to 491 per second on fef94e7, over bursts of a few seconds, are 680 to 1,400 times it. The comparison also ignores repository size, which rules out one Artifacts repository for a Scion-sized history, the cost of checks, which this platform runs before landing, and the read traffic of tens of millions of checkouts per day.

8.7 Sensitivity

The authority’s per-call cost matters most for the polling configurations. At 1.0 ms the C1 peak rises to about 19.5 landings per second near 1,300 agents; at 5 ms, the slowest rate Cloudflare’s guidance allows for complex work, the C1 peak falls to about 7 near 550 agents and the C2 peak to about 12 near 800. C3 holds about 11 landings per second across the whole range of sss. The measured step of 10.5 to 12.5 s at 03821e0 puts C3 between about 10.2 and 12.2 landings per second, and the early cycle’s range of 2.4 to 2.6 s puts the C1 and C2 ceilings between 24.6 and 26.7. A faster poll iteration in C2 hurts: at 0.15 s its peak falls to about 22.5. The knee scales with Z+R0Z + R_0Z+R0​: at Z=10Z = 10Z=10 s the C1 and C2 peaks fall to about 300 and 350 agents, and at Z=600Z = 600Z=600 s no configuration saturates below 10,000 agents. 9 Planned evaluation

This section states the planned evaluation for the whole series; Parts I and II cite it for the measurements they lack. Each item gives the method, the metric and the outcome that would confirm or refute the expectation. No results are reported.

Batched landing at a sustained rate.

The developers’ targets are 100 of 100 landings with landing p95 at most 2 s at 100 writers, which both 100-writer runs on fef94e7 meet, and 1,000 of 1,000 landings at a sustained rate of at least 50 per second at 1,000 writers, which no run has tested. The 1,000-writer runs landed every change at 235 to 491 per second over bursts of a few seconds, which is a burst average, not a sustained rate. Run open-loop arrivals at fixed rates from 50 to 800 landings per second for at least ten minutes each on a revision of the development branch, from one client, and log the batch size and duration of every authority batch call. The target is met if the sustained rate reaches 50 per second with no refused landing or read; the batch log tests the capacity relation directly, and the highest rate held without refusals locates the knee.

Reads under bursts.

On fef94e7 every read succeeded because reads of main came from the cached published head; with reads served by the authority, 540 of 1,000 succeeded. Repeat the 1,000-writer burst with each read source, count refused reads with the other refusals, and treat any refused read as a failure of the run, so that the cost of reading from the authority under load is measured rather than avoided.

Commits under a shared login.

With one shared login, commit p95 at 1,000 writers missed 1 s in all three runs. Time the authorization phase per request across the burst to test whether the shared session’s checks, not the commit path, account for the difference.

Write skew in a batch.

The benchmark cannot produce write skew, because each writer writes its own file and declares no reads. Add a workload whose writers read files that other writers in the same batch write, and measure how often the within-batch check of Part I defers a member and what it costs per batch.

From 100 to 1,000 writers.

Repeat the hosted burst with 100, 250, 500 and 1,000 writers on one committed revision with Server-Timing enabled, five runs per size from one client location, and record the deployed revision and the cleanliness of its tree in the output. The series begins by repeating the early group’s instrumented runs on a recorded revision. Run each size twice: once as today, with every writer landing after its commit, and once with commits only, so that landing calls do not overlap the commit tail. The metric is commit acceptance p95 and the per-phase sums. The commit-only series tests the burst predictor of Eq. (3). A second series replaces the burst with open-loop Poisson arrivals of landings at fixed rates from 2 to 30 per second, recording throughput and the authority’s call rate, to locate the C1 plateau and test for the collapse that Corollary 6.12 predicts.

Per-tier hit rates.

The edge served every warm read in the hosted benchmarks, and the one measurement that reached R2, the reads of a single cold check, gave an R2 hit rate of 0.984. Measure hit rates per tier against the platform’s 99 percent target, taken from Scion’s published design, with cold reads from several client locations, reads after an edge eviction, and the reads of many Container check runs on a recorded revision. A tier below 99 percent under a realistic read mix refutes the claim that the tier structure carries that caching property. A local test already shows that 20 concurrent cold misses of one object cause 20 origin reads, so request coalescing is a known gap.

Real-model arms.

The companion paper proposes Study A, which crosses three repository layouts with file-level and symbol-level interfaces, and prediction P9, that dependency-aware scheduling reduces makespan and integration failures relative to file-disjoint scheduling [8]. The platform provides the symbol interface, declared read sets and the planner that P9 needs. The planned runs use the companion paper’s metrics (closure recall, exposure precision, and cost per accepted change, its Eq. 12) and its cluster-aware inference with repositories as clusters. The scripted evaluation program exists, and the early real-model runs are too small to report.

10 Deviations from Scion

The platform follows Scion’s principles but departs from its architecture in four ways, each with a cost that the measurements make visible.

Git objects instead of changesets.

A Scion changeset lists the files changed relative to its first parent and points at content-addressed blobs; it needs no tree objects [3]. The measured revisions build real Git blobs, trees and commits on the commit and landing paths. That was a choice of the realization, not a requirement: what the design needs is Git’s semantics of commit, branch, merge, diff and log, and the changeset landing of Section 5.4 builds main’s Git objects in the background as a deterministic projection of the log. In the measured revisions each commit writes new tree objects along every changed path. Part I’s incremental rewrite keeps the cost proportional to the change (its Proposition 4.3), which the flat one-file commit cost on repositories of 100 and 3,000 files confirms, and in the early revisions each commit wrote those objects to R2 and Artifacts before it was acknowledged. The Scion post credits Mononoke, the server of Meta’s Sapling, with pioneering many of Scion’s techniques, especially the Bonsai data model of flat file changes [3, 35].

One authority per repository instead of one row per ref.

Scion moves a ref by a compare-and-swap on a single Spanner row, separate from changeset creation [3]. Here the compare-and-swap is a transaction in the repository’s Durable Object, with the same single-row semantics, but the object holds every ref of the repository and also serves commit preparation and recording. Commit creation therefore passes through the same serial resource as ref moves, which is why the burst’s delay appears at the authority and why C2 exists. Scion’s ref store grows by rows; this platform grows by sharding repositories, so one hot repository is the unit of capacity.

An approval gate before the main branch.

Scion lands without a global merge lock and invests in testing after merge [3]. This platform requires human approval or policy auto-approval and required checks before a landing. The gates are a fixed cost on the land path. In the one measured pair, a Container check took 8.1 s from a warm-start seed and 109 s cold, so a landing that waits for a check waits far longer than the combiner’s cycle. The capacity projections exclude check time; they assume gates are already satisfied when a landing is enqueued, as the code requires.

Many repositories instead of one monorepo.

The platform hosts many repositories per workspace, each with its own authority and push queue, so the authority’s limits apply per repository. The Scion-scale question becomes the capacity of one hot repository, which is what Section 8 projects, and a fleet spread over many repositories does not contend at all.

Two smaller deviations follow from these. Checkpoints are written every 64 versions into the authority’s SQLite database rather than to object storage, which is simpler but adds to the 10 GB limit. And a batch of landings becomes one octopus merge commit that keeps the landed commits’ identifiers, whereas Mononoke’s pushrebase rewrites commits onto the new head to keep history linear [36].

11 Threats to validity

One account, two clients.

All hosted runs used one throwaway Cloudflare account on the paid plan. The live benchmark ran on one developer machine and the fan-out benchmark in one client Worker in us-east-1, and every latency includes its client’s network path, and the placement of the Durable Objects relative to the client was not controlled or recorded. Round trips of about 50 ms per authority call in an idle repository suggest that the network path is a first-order term, so latencies from another location could differ substantially.

Few runs and code drift.

The early 100-writer burst was run four times, on three code states, and the later runs span more than a dozen revisions with few runs each. The p95 of 100 samples is set by five requests, and the spread of p95 across runs was 0.93 s. Two runs lost 7 and 9 commits, which were excluded from their percentiles; their p95 values would be higher with the failures counted as slow. The deployed revision of the two instrumented early runs was not recorded in their output, the hosted benchmarks never record whether the deployed tree was clean, and the one polling run from the us-east-1 client survives only in a session transcript with an inferred revision. No output of a later run is a committed file; every one is an uncommitted output copied into the project’s evidence.

Synthetic workload.

Each writer adds one tiny new file to a 100-file repository in a closed burst with no think time. There are no conflicting writes, no merges of the same file, no read-heavy mix, and no open-loop arrivals. Real agents write larger changes, so commits would carry more objects and longer prepares.

Measurement semantics.

Server-Timing phases are sums of waits measured in the Worker, not CPU time, and Workers clocks do not advance during computation. A percentile of a sum is not the sum of percentiles, so the decomposition of the median in Section 5 cannot be applied directly to the tail. The batch size per claim was not logged, so the mean batch is inferred from rounded call counts.

Platform behavior.

Artifacts is in beta. The one-receive-pack limit is observed, not documented, and could change. The R2 key behind the failures in H4 is unidentified.

Redesigned-landing runs.

The fef94e7 results come from one deploy and one client; the deployed platform was a clean build of fef94e7, but the bench client carried an uncommitted change that reports commits per shard. There were three runs per principal mode at 1,000 writers and one per mode at 100; only the third 1,000-writer run of each mode kept its full output, and the first two survive as summary lines. Their rates count from the first landing request to the last answer of a closed burst lasting a few seconds, so they are not sustained rates. The controlled comparison on dd6c9a8 used a branch revision, one run per mode and size, and two of its six output files name a later commit than the deploy, an attribution that rests on the session record.

Acceptance semantics.

The commit p95 under 1 s of the later revisions counts a commit as accepted once a Durable Object holds its objects, before R2 or Artifacts does. A commit accepted in this sense survives a Worker failure but depends on the projector to reach the store of record, and a reader of the store of record may not see it yet. The early revisions’ figures use the stricter meaning, so the two groups do not measure the same event.

Local evidence.

One local run has raw output; the earlier local figures exist only as approximate values in a commit message, and the simulated latencies of workerd do not resemble the hosted network path. The local per-call cost used in Section 7 comes from a different Durable Object class with a different schema.

Model assumptions.

The projections rest on landing behavior that no run has observed at sustained saturation. The capacity model treats every authority call as equally expensive, treats agents as a closed population with a fixed think time, takes the combiner’s cycle as independent of batch size, and assumes that configuration C2’s combiner keeps the early cycle, which was measured under load. Its service time comes from a different authority class measured locally. Its calibration covers commit tails under one burst size. The 1,000-writer bursts did saturate the authority, but they are bursts, not the steady state that the projections describe, and the collapse the model predicts for polling configurations is a fixed-point result whose onset and depth depend on these assumptions. The changeset landing is measured but not modelled.

12 Related systems

The question of how fast a log-structured table can commit has a known answer for object stores. Delta Lake commits by atomically creating the next log entry, and its authors observe that the commit rate is bounded by the latency of that atomic step, which for object-store put-if-absent allows several transactions per second per table; they suggest batching and a low-latency coordination service as remedies [1]. Apache Iceberg commits by an atomic swap of a metadata pointer with optimistic retry [37]. The repository authority plays the role of Delta’s low-latency coordinator, and the land combiner is the batching. The measurements here put numbers on both: the atomic step itself takes about 86 ms as a hosted round trip, and the batch cycle around it takes about 2.6 s.

Scion places its ref compare-and-swap in Spanner [3, 9], which scales by distributing rows. Mononoke’s pushrebase moves a bookmark by rebasing the pushed commits on the server when they touch different files, retrying on conflict [36]. Part I (its Section 11) compares the concurrency control of these systems in detail; this Part adds the observation that on a serverless platform the cost of a ref move is dominated by the calls around it, not by the move. Google’s Piper is the best-documented earlier case of one repository serving a large company [38].

13 Conclusion

The transaction system of Parts I and II needs six primitives, and their contracts are small: content-addressed puts and gets, a linearizable compare-and-set with a log append per repository, at-least-once queues, stateless and container compute, and an optional Git projection. On Cloudflare each maps onto one product. The commit path on that realization missed its 1 s target in early revisions, with p95 between 2.8 s and 3.7 s across four runs, and met it in 28 of 39 later runs once commits were acknowledged when a Durable Object held them.

Landing was the harder problem, and the measurements say where it lies. Landings that built Git trees and merge commits on the critical path failed under a burst of 1,000 writers. Landings that append changesets to the log in batches and project Git objects afterwards, merged into the development branch at fef94e7, landed all 1,000 changes in each of six bursts without a refused commit, landing or read, with landing p95 of 1.21 to 3.03 s. A queueing model over primitive service times reproduces the early commit tails and predicted that polling landings would fail first, which they did, though by refusal rather than by unbounded delay.

What the foundation enables is a source-control system whose correctness rests on a transaction log and whose cost can be stated per primitive before it is built on any particular cloud. What remains open is a sustained landing rate, which no run has measured; reads served by the serialized authority, which it still refuses under a burst; commit p95 under 1 s for writers that share one login; a delay of several seconds before main’s Git commit exists; and a workload that exercises write skew within a batch.
