1 Introduction

Source code and source control are now transactional abstractions. The series this paper belongs to treats a repository as a database: a change is a transaction with a read set and a write set, landing a change is a commit under optimistic concurrency, and a version is a snapshot [19]. Derived data complete the picture. A search index, a symbol table or a blame is a view of a snapshot, and it must stay consistent with the snapshot it claims to describe while many transactions land. This Part lays that piece of the foundation: a definition of derived data as views over the transaction log maintained incrementally by partitioned jobs, the condition under which incremental maintenance is correct at a snapshot, and a working realization in which one view violates the condition.

We argue that the next evolution in code is transactional, and the argument rests on precedent. Data lakes began as files on object stores. Concurrent writers and derived computation broke file-level semantics, and the field moved to tables with a transaction log, snapshots and optimistic concurrency [3], over which Spark-style partitioned computation runs [28]. Source control is under the same pressure, because agents multiply both the number of concurrent writers and the volume of derived work, and for code the derived work, from search and symbols to checks and the Git objects themselves, becomes views over the log. Scion’s published design makes the same move: changesets are entries in a log, created separately from ref updates, and a ref moves by compare-and-set on one database row [2]. The proofs and measurements of this series support the thesis; they do not settle it.

A repository holds two kinds of data. Inherent data are the commits, trees and blobs that users write. Derived data are everything computed from them: the trigram index that answers code search, the table of symbols in each file, the attribution of each line to the commit that last changed it, the history of a path, the review class of a change, the result of a check on a commit. A repository with one human committer can recompute most derived data on demand. A repository that lands tens of thousands of changes per day cannot. The Scion post reports more than 30,000 merges per day at Anthropic in September 2026 [2] and describes derived data as values defined recursively over a changeset’s parents and computed by one generic mechanism [2]. Mononoke, the server of Meta’s Sapling, implements the same idea through a trait whose central method derives a value for one changeset from its Bonsai representation and its parents’ derived values [25].

The question this paper answers is when such reuse is correct and what it costs. The answer has to be precise because the failure mode is silent. A stale or misattributed index returns plausible results. An incremental build that reuses the wrong partition produces a search hit at a path that does not exist, or a codemod that skips a file, and nothing in the request reports an error.

Part I treats the repository as a Delta-style table: an append-only transaction log, snapshots identified by log versions, and optimistic concurrency with backward validation [3]. This Part treats derived data as Spark-style partitioned jobs over those snapshots [28]. A job names a snapshot commit, a partitioning of its tree, a task kind and a policy. Map tasks read immutable objects through the object tiers and write one segment per partition. A reduce combines segments into the answer. Write jobs, such as a repository-wide literal replacement, reduce instead into a single commit that enters the transaction log through Part I’s validation.

The architecture is stated over cloud-portable primitives, and YonedaRepo, the system under study, is its reference realization on Cloudflare. The author designed and built YonedaRepo, which is still being built; its code is cited by file and commit throughout and in Appendix A.

Its derived-data layer partitions a commit’s root tree by top-level directory, keys each directory’s segment by the directory’s Git tree id, and stores segments in the object store under that key. The design notes describe the goal as “only changed partitions recompute”. A test confirms the behavior on a three-partition repository: the first query builds three segments, a query after a change to one directory builds one, and a query pinned at the earlier log version builds none (Section 14).

We make six contributions.

  1. A job model and a formal definition of content-local and history-dependent derivation kinds over the commit DAG (Sections 3 and 4).

  2. A view-consistency theorem: partition reuse equals full recomputation exactly when the storage key is sufficient for the map function, with a work bound proportional to the changed partitions and a soundness result for pruning by the log’s touched paths (Section 5).

  3. A view-consistency failure in the reference implementation. The search segment key omits the directory prefix, while the segment records full paths, so the key is not sufficient and the maintained view can disagree with its snapshot. We give two repairs and prove both correct (Section 7).

  4. An analysis of write jobs. A codemod is atomic, and it is serializable with concurrent landings only if it is confined to a directory that it declares as a read, or if it lands as a fast-forward (Section 9).

  5. Properties of the symbol-level plan DAG, including the exact sense in which Tarjan components and stages realize the companion paper’s independence condition and critical-path bound [21], and the condition under which the planner inherits the companion paper’s representation invariance (Section 10).

  6. Git compatibility as a derived view: the Git commits of main are a deterministic projection of the log, rebuilt incrementally, with a measured staleness (Section 13).

The evidence for correctness is tests, and the evidence for cost is almost absent. The tests are the repository’s unit and property-based tests and a test we wrote against the code at commit cfa4845 that executes the counterexample of Section 7. The only timings that touch derived data are the commit-time derivation phase in two instrumented hosted runs and the warm-start seed figures from commit messages. Indexing throughput, segment sizes, the fraction of partitions that change on real repositories and the cost of a codemod were not measured; Part III, Section 9 lists the planned measurements [20].

Concurrency control works on accesses. Accesses are file paths, directory prefixes written dir/, or symbol entries path#symbol, with an overlap relation ⋈\bowtie⋈ (Part I, Definition 4.4). Landing a change validates it backward against the entries that landed after its base version, with outcomes fast-forward, rebase, merge or conflict (Part I, Definition 4.15).

The proofs of Sections 9 and 12 rest on four results of Part I, which we use in the following form.

(P1)

Validation of a change with base bbb and declared reads R\mathsf{R}R returns a conflict if some later entry on the same ref is opaque or has a refined write that overlaps R\mathsf{R}R; otherwise it returns fast-forward, rebase or merge, and in the last two cases the platform appends a merge commit whose parents are the previous head and the landed commit (Part I, Definition 4.15).

(P2)

If validation does not return a conflict, the tree after landing equals the tree before landing with the change’s writes applied, and the declared reads agree between the base and the state just before landing (Part I, Theorem 6.4).

(P3)

The land combiner validates each batch member against the log but not against the other members, so a batch can contain two members that each write what the other read (Part I, Theorem 7.3); if the combiner also refuses a member whose reads overlap the writes of an earlier accepted member, the batch is equivalent to landing its members one at a time in ticket order (Part I, Proposition 7.4).

(P4)

If a ref holds commit xxx at version uuu, then at every later version its value reaches xxx by first parents (Part I, Theorem 5.4).

One property of Git objects carries most of the arguments below. A tree object lists names, modes and object ids of its entries, and its own id is the hash of that listing [15]. Trees therefore form a Merkle structure [22].

Assumption 2.1 (Collision resistance). Over all objects a repository ever stores, distinct object contents have distinct ids. The same holds for the platform digest HHH over the values it is applied to, each of which is encoded unambiguously before hashing. Part I makes the same assumption for object ids in all its results (Part I, Section 4).

Lemma 2.2 (Subtree identity). Under Assumption 2.1, two stored trees have the same id if and only if they have the same entries recursively: the same names, the same modes and the same file contents at every path. In particular, for commits c,c′c,c'c,c′ and a prefix ppp, id(τ(c)∣p)=id(τ(c′)∣p)\mathrm{id}(\tau(c)|_p)=\mathrm{id}(\tau(c')|_p)id(τ(c)∣p​)=id(τ(c′)∣p​) if and only if every file below ppp has the same mode and content in both commits.

Proof. If the ids are equal, Assumption 2.1 gives equal tree contents, so the entry lists are equal. Equal entry lists contain equal child ids, and induction on depth gives equal subtrees and blobs at every path. Conversely, Git serializes a tree with its entries in a canonical order determined by name and mode, so recursively equal trees serialize to the same bytes and hash to the same id [15]. ◻

The lemma is the reason a tree id can stand for the content of a whole directory. It says nothing about where the directory sits. Two directories with different names and identical content have the same id, and this fact is the source of the defect analyzed in Section 7.

Lemma 2.3 (Commit ids determine ancestry). Under Assumption 2.1, the id of a commit determines its root tree, its parent ids in order, and recursively the root trees and parents of all its ancestors.

Proof. A commit object contains its tree id and its parent ids [15]. Equal commit ids give equal commit objects, hence equal tree and parent ids; induction along parents gives the rest. ◻

The job model needs four primitives besides Part I’s serialized authority, which holds the log. An object store holds segments under keys, with puts and gets. A durable queue delivers derivation jobs at least once, with retries. Stateless compute runs map and reduce tasks as request handlers. Container compute runs checks. The results of this Part are stated over these primitives and use only the properties just listed, plus the read guarantee of Assumption 5.2. The reference realization uses Cloudflare R2, Queues, Workers and Containers, and Part III, Table 1 maps each primitive to its realizations [20].

Some limits of the reference realization bind derived data, and each comes from one realization’s choice, not from the design. Each Worker invocation, the stateless-compute primitive here, allows six simultaneous outgoing connections and a fixed subrequest budget [9], which bounds how many partitions one invocation can build at once. R2, the object store here, allows one concurrent write per second to a key [8], which matters only when two jobs write the same key. Another realization would change these numbers and leave the theorems untouched. Part III, Section 4 treats the limits in full.

3 The job model

Definition 3.1 (Partitioning). Let ccc be a commit whose root tree has directory entries d1,…,drd_1,\ldots,d_rd1​,…,dr​ and non-directory entries FFF. Code search is the main content-local kind. Its reduce answers a query by intersecting postings in each segment, reading candidate blobs, matching lines and concatenating the per-partition results up to a limit.

The Rust operations never fetch objects themselves. A map task’s input is therefore exactly the content its key names, even when the adapter is not trusted.

Jobs run at two times. A landing that moves a ref enqueues on the durable queue a message naming the repository and the ref. In the reference implementation the message has kind platform_derive (repo-tools.ts), and the consumer, a Cloudflare Queue configured with batch size 1 and three retries, reads the ref’s current head and builds its search segments and a warm-start seed for check runs (deriveAfterLanding in repo-derived.ts). A query that finds a segment missing builds it on demand. Because the message names the ref and not the commit, a burst of landings produces messages that each derive whatever head is current when they run. Later messages find their segments already built and do no map work. This coalescing is correct by Theorem 5.3, since a job duplicated by at-least-once delivery, or delayed, computes values that are already in the store or that the store would hold anyway.

4 Derived data as a fold over the commit DAG

The Scion post and Mononoke define derived data recursively from parents. Content addressing defines it from the tree. The two definitions agree for content-local kinds, and the difference between them is what content addressing can reuse.

The definition says nothing about cost. Its value is that Φδ\Phi_\deltaΦδ​ may look only at the change from parents to child, so a good Φδ\Phi_\deltaΦδ​ costs in proportion to the change.

5 Incremental correctness

Definition 5.1 (Key sufficiency). A key function κ\kappaκ is sufficient for a map function fff if, for all partitions (p,x)(p,x)(p,x) and (p′,x′)(p',x')(p′,x′) that can occur in any commit, κ(p,x)=κ(p′,x′)  ⟹  f(p,x)=f(p′,x′).\kappa(p,x)=\kappa(p',x')\;\Longrightarrow\;f(p,x)=f(p',x').κ(p,x)=κ(p′,x′)⟹f(p,x)=f(p′,x′).

Sufficiency says that the key determines the segment. It is the condition under which a stored segment may be returned for any partition that has its key. The build-systems literature states the same requirement for constructive traces, where a stored result may be reused whenever the hash of the task’s inputs matches [23]. The difference here is that the key is chosen per kind by the system designer, and nothing in the platform checks that the choice is sufficient.

The argument depends on keyed storage, and a derived stream that is appended rather than keyed does not inherit it. The platform also emits a change log of landed changes to an analytics sink, and concurrent derivation jobs for one repository read the same cursor and re-sent the same range. Before commit 3cc14b1, the commit message reports a 2.7-fold duplication of change-log rows on the hosted deployment. The fix claims each range with a put conditioned on the cursor’s entity tag before sending, so the losing job stops, and a failed send moves the cursor back, which keeps delivery at least once. This is the role that an atomic commit of task output plays in MapReduce [11, Section 3.3]: a keyed segment needs no such step, and an appended record does. No hosted measurement after the fix exists.

Theorem 5.3 is an instance of established memoization results, and its proof is the reduction. In the terms of Mokhov, Mitchell and Peyton Jones, the segment store is a store of deep constructive traces: a result is filed under a hash of the task’s terminal inputs, here the subtree its key names, and such traces are correct only for deterministic tasks [23, Section 4.2.4]. Key sufficiency is the requirement that the trace key cover every terminal input, and Assumption 5.2(i) is their determinism requirement. Duplicate execution is harmless for the reason MapReduce gives: deterministic operators produce the output of a non-faulting sequential execution [11, Section 3.3]. Resilient distributed datasets rely on the same facts to recompute a lost partition from its lineage [28, Sections 1 and 2.1], and the key plays the role of lineage here.

Two assumptions of those sources differ in our setting. MapReduce keeps one output per task through an atomic commit of its output [11, Section 3.3], while the segment store tolerates several equal puts and needs no atomic rename. And a build system’s trace key is computed by the system from the inputs a task actually reads, while here the key function is chosen per kind by its designer and the platform never checks that it is sufficient; Section 7 shows what that costs.

6 Search as a partitioned read job

Search is the derivation kind with the clearest Spark structure. The companion paper compares semantic indexing to Splunk’s distributed search, in which a search head dispatches a query to search peers and assembles their results [21]. In YonedaRepo the head is the Worker invocation that handles the query and the peers are the stored segments; there is no separate peer process. The head plans the partitions of the commit’s root tree, obtains each segment, asks the Rust search_segment operation for candidates in each, filters candidates by the caller’s grant before any candidate’s content is read for matching, reads each remaining candidate blob and matches lines, and concatenates results in partition order up to a limit of 200, 50 by default. Building a segment reads every blob of its partition regardless of who asked; the grant governs what a query returns, not what the index contains.

The index follows Cox’s design for regular-expression search with trigrams [10], restricted to literal queries. It is sound for indexed files.

Proposition 6.1 (Candidate superset). Let qqq be a query that the adapter accepts (2 to 200 UTF-16 code units) and FFF an indexed file of a segment. If the bytes of FFF with ASCII letters folded to lower case contain the bytes of qqq folded the same way, then FFF is among the candidates the segment returns for qqq.

Proof. The code folds ASCII case byte by byte in both the content and the query and extracts the set of three-byte windows that contain no newline byte. If the folded query has no such window, which happens when no newline-free run of the query is three bytes long and in particular for any query of at most two bytes, the content filter is absent and every indexed file is a candidate. Otherwise every window of the folded query occurs inside the folded content of FFF, because a substring’s windows are windows of the containing string and the newline filter treats both the same way. So FFF appears in the posting list of every window of the query and in their intersection. ◻

Search is complete only for ASCII-folded matches in indexed files of indexed partitions. Both the trigram extractor and the line matcher fold case on ASCII bytes alone, so a query that differs from the content in the case of a non-ASCII letter does not match. Binary files and files over 1 MiB are never content candidates and match only by path. A partition with more than 20,000 files has no segment and is reported to the caller in skipped_partitions.

Within those bounds the reduce returns exact matches, in partition order and in each segment’s file order, up to the limit. Each candidate is narrowed by exact line matching on its verified blob. When matches exceed the limit, which of them are returned therefore depends on how the repository is partitioned.

How far the harm extends depends on where the stored segment came from. Segment keys are scoped to one repository, and directory grants restrict paths at every commit (Part I, invariant I14), so the leaked bytes always existed under the reported path in some commit of the same repository. When that commit is an earlier commit on a branch the caller can read, only the attribution is wrong. When it is a commit the caller cannot discover, such as unlanded work of another writer, the caller receives content it had no practical way to reach.

Prefix-free keys also corrupt results within one commit whenever two top-level directories a/ and b/ have identical content. On a cold store, the first query builds a segment for each directory with its own prefix and returns correct paths, but both writes target one R2 key. Every later query reads the one stored segment for both partitions and reports each match twice under one prefix and never under the other. Two writes to one key within a second can also exceed R2’s per-key write limit [8]; we have not observed this.

Prefix-free keys make a codemod either fail permanently or leave a directory unedited. After the rename of src/ to lib/, the codemod reads the stale segment and emits changes for src/… paths, each with an expected old blob. The parent tree has no such paths, so commit preparation rejects the commit with CONFLICT (prepare.rs), and it does so on every retry because the stored segment never changes. With duplicated directories, the reduce receives two identical changes for each matching path under one prefix and none under the other, so either the commit is refused or one directory is left unmodified.

A test confirms the key collision; no test in the repository covers it. We wrote the test against the Rust crates at commit cfa4845 and ran it outside the repository (Appendix B). For a commit with identical top-level directories a/ and b/, and for a rename of src/ to lib/, it asserts that search_plan gives both partitions the same key and that index_partition builds segments listing different paths. The recursive form restates one step of the induction; since Blame(c′)\mathrm{Blame}(c')Blame(c′) pairs ownm−1\mathrm{own}_{m-1}ownm−1​ with the lines of v(c′)v(c')v(c′), the update is a function of ccc and Blame(c′)\mathrm{Blame}(c')Blame(c′) alone, as Definition 4.1 requires. ◻

The implementation evaluates the fold from scratch at every query, so a blame costs one diff per version of the file, over the newest versions that the request reads from path history: 200 by default, and at most 1,000 because path history caps its limit. Versions older than that window are attributed to the oldest version kept, which acts as a history boundary in the manner of git blame’s caret.

The proposition describes the untruncated fold. With the window, the oldest kept version moves as new versions arrive, so the windowed blame of ccc is not an update of the windowed blame of c′c'c′. Memoizing the untruncated fold under the key (id(c),p)(\mathrm{id}(c),p)(id(c),p) would remove the window and reduce the cost to one diff per landed change to the file, and Corollary 5.9 makes that memoization correct. This is the recursive blame the Scion post describes [2], and YonedaRepo does not yet have it.

Blame and path history also follow only the first parent. Changes reached only through a merge’s other parents are attributed to the merge, and neither computation follows renames.

Rename detection is change-local and exact. The tree diff pairs a deleted file and an added file with the same blob and mode into one rename, which matches git diff -M100% (with_renames in platform_compute.rs). A rename with any edit is reported as a deletion and an addition. Copy detection is not implemented.

Check results are derived data with a policy in the key. A run is bound to the exact commit, the check name and the digest of the landing policy, and only completions from the run’s current epoch count (checks.rs). Changing the policy changes the digest, so results recorded under the old policy stop counting for gates. The key (id(c),check,digest)(\mathrm{id}(c),\text{check},\text{digest})(id(c),check,digest) is sufficient only for a deterministic runner. A flaky test makes the result an observation rather than a function, and reusing it is a policy choice that the theorem does not justify.

Bisect uses check results as its oracle. Given a good commit ggg and a bad commit bbb on one branch, its candidates are the first-parent commits after ggg up to bbb, at most 10,000 (bisect.rs). Each step reads the check result at the midpoint, requesting a run if none exists under the current policy, and halves the range.

Proposition 8.2 (Bisect). Let x1,…,xnx_1,\ldots,x_nx1​,…,xn​ be the candidates, with xn=bx_n=bxn​=b taken as failing without a run, and suppose the check is deterministic and monotone along the chain: once it fails at some xix_ixi​, it fails at every xjx_jxj​ with j≥ij\ge ij≥i, and it passes at ggg. Proof. The invariant is that the first failing candidate lies in the current range (ℓ,u](\ell,u](ℓ,u], where the check passes at ℓ\ellℓ (initially ggg) and fails at uuu (initially xnx_nxn​). Testing the midpoint and replacing ℓ\ellℓ or uuu by it preserves the invariant by monotonicity and halves the number of candidates in the range, rounding up. After ⌈log⁡2n⌉\lceil\log_2 n\rceil⌈log2​n⌉ steps the range contains one candidate, which is the first failure. Results that already exist under the policy digest are reused and cost no execution, so the bound counts at most one execution per step. ◻

The repository’s test bisects seven candidates with an injected regression at the fourth and asserts at most three executions on candidate commits and the correct answer (Section 14). Without monotonicity the procedure still terminates at a boundary where a passing candidate precedes a failing one, but that boundary need not be the first regression.

Warm-start seeds are a content-local kind computed eagerly. After a landing, the derivation job writes to R2 one object containing every file at the branch head, and a check run on a nearby commit starts from the seed and fetches only the blobs that differ (repo-seed.ts). A seed write that fails costs only speed.

Seeds are the one derived kind with a measured benefit, and the measurement is thin. The commit that introduced seeds reports that a seeded hosted check run on a nearby commit of a 301-file repository fetched 1 of 301 blobs and took 8.1 s against 109 s for the first cold run, most of which was Container start. The same commit reports 1 against 201 blob fetches in the local test. These three figures come from a commit message and have no raw output on disk.

9 Write jobs

Definition 9.1 (Write job). A write job over commit ccc at log version vvv is a job whose map function sends each partition (p,x)(p,x)(p,x) to a set CpC_pCp​ of file changes below ppp and whose reduce forms the single commit with parent ccc, base version vvv and change set C=⋃pCpC=\bigcup_p C_pC=⋃p​Cp​. The commit then lands through Part I’s validation (Part I, Definition 4.15).

The implemented write job is the literal codemod in codemod in repo-code.ts. It obtains the search segments of the head, takes in each partition the candidate files for the find string that the caller’s grant allows and that lie under an optional path prefix, and asks the Rust replace_literal operation to replace every non-overlapping occurrence in each candidate. A changed file becomes a change carrying the new content and the old blob id as its expected value. The reduce concatenates the changes and creates one commit on the head, with the head’s version as base. It does not land the commit.

Proposition 9.2 (Codemod reduce). Assume the search key is sufficient (Section 7). Then: (a) the sets CpC_pCp​ are pairwise disjoint in paths, so CCC contains at most one change per path; (b) every expected blob id in CCC matches the parent tree, so commit preparation accepts CCC; (c) the job creates either one commit containing all of CCC or no commit; and (d) two runs with the same head, find string, replacement, prefix and grant produce the same tree, although their commit ids may differ.

Proof. (a) Each CpC_pCp​ contains only paths below ppp, and partitions of one commit are disjoint in paths. (b) By Theorem 5.3 the segments are those of the head, so each candidate’s blob id is the head’s blob at that path, and replace_literal returns that id as the expected value. (c) All partitions run under one Promise.all; any failure rejects the request before the single call that creates the commit. Commit preparation is itself all or nothing, and the commit enters the log as one entry, as a Delta transaction commits as one log record [3]. (d) The replacement is a deterministic function of the blob and the arguments, the candidate set is a deterministic function of the segments and the grant, and the tree of a commit is determined by its parent’s tree and its changes. The commit object also carries the request time in seconds, so its id need not repeat. ◻

The codemod’s result is complete only for indexed files. A file over 1 MiB is never a candidate and is never rewritten, and a partition over 20,000 files is skipped. The codemod’s response reports the number of partitions but not which were skipped, so a caller cannot tell that the replacement was partial.

Rerunning a codemod on its own output changes nothing exactly when the output contains no occurrence of the find string. The repository’s test checks the empty case: a codemod for a string that occurs nowhere returns changed: false.

A codemod that declares no read set admits write skew under backward validation. A codemod reads every candidate in every scanned partition, and its result depends on the absence of the find string elsewhere. The commit it creates declares no read set. Under Part I’s backward validation, an entry that landed after version vvv and touched one of the codemod’s files is a write-write overlap, which leads to a content merge rather than a conflict, and an entry that touched only other files leads to a rebase (Part I, Definition 4.15). In both cases the codemod lands. A file that gained an occurrence of the find string after version vvv is not rewritten, and the landed tree contains the old string. This is write skew in the sense of Berenson et al.: each transaction is valid against a snapshot, and their combination is not equivalent to any serial order [4].

The codemod at commit cfa4845 neither accepts nor declares a read set, so Proposition 9.3 below characterizes a proposed extension of its commit request. Declaring a directory as a read is a predicate read in the sense of Fekete et al. and Adya: a read of every item that satisfies a predicate, here every path below the directory, including paths added later [14, Definition 2.1] [1]. Delta Lake’s conflict checker performs the corresponding test, failing a transaction when a concurrent commit added files that match its partition read predicates [12]; the difference is that Delta derives the predicate from the query, while here the writer declares it.

Proposition 9.3 (Serializable codemods). Assume the search key is sufficient. Let a codemod over version vvv be restricted to a directory prefix q/q/q/, so that it reads and writes only paths below q/q/q/, and let it declare the read set R={q/}\mathsf{R}=\{q/\}R={q/}. Suppose that the top-level partition containing q/q/q/ is within the indexing cap of 20,000 files at vvv and also immediately before the landing; the second condition follows from the first when q/q/q/ is itself a top-level directory. If its commit lands by itself, or in a combiner batch that satisfies the acceptance rule of Part I, Proposition 7.4, the landed tree below q/q/q/ equals the codemod applied to the snapshot immediately before its landing.

Proof. By (P1), validation returns a conflict, and the landing is refused, whenever an entry after vvv on the same ref has a refined write that overlaps R\mathsf{R}R. Every path below q/q/q/, including a path added after vvv, and every symbol of a file below q/q/q/ overlaps q/q/q/. So a landing succeeds only if no entry after vvv touched a path below q/q/q/, and then the subtree at q/q/q/ is the same immediately before the landing as at vvv. Because the enclosing partition is indexed at both versions and the key is sufficient, the codemod applied to that snapshot computes the same candidates below q/q/q/ and the same changes. When q/q/q/ is top level, its partition’s size changes only through writes below q/q/q/, which validation refuses, so a partition within the cap at vvv is still within it. By (P2), the landed tree equals the pre-landing tree with the codemod’s changes applied on its write set, which is the claim. Inside a batch, the acceptance rule in (P3) makes the batch equivalent to landing its members one at a time in ticket order, and the same argument applies to each. ◻

Without the batch condition a declared read does not protect a codemod. By (P3), the combiner at commit cfa4845 validates batch members against the log but not against each other. A codemod that shares a batch with a commit adding an occurrence of the find string in its scope would land, and the new occurrence would survive.

A repository-wide codemod cannot be made serializable by declaring reads. Such a codemod scans every top-level directory and the root files, and a declared set of those directory prefixes and file paths does not cover a top-level directory or root file added after vvv. A concurrent commit that adds such a file containing the find string writes nothing the codemod declared, validation returns a rebase, and the new occurrence survives. Part I’s access entries have no form that covers the whole repository, so the only condition that makes a repository-wide codemod serializable is that its landing be a fast-forward, with no entry on the ref after vvv. Declared reads also cost refusals. Any concurrent landing in scope forces the codemod to rerun, and the rerun is the only way to rewrite a new occurrence.

Retrying only a failed partition requires memoizing the codemod’s map outputs. The design notes promise that a failed partition is retried alone. The code reruns the whole job, which re-reads segments from the store but repeats every replacement. Memoizing the map outputs gives partition-level retry with the same correctness argument.

Proposition 9.4 (Partition-level retry). Store each CpC_pCp​ under the key (codemod,  H(⟨find,replace,prefix,grant,p⟩),  κ(p,x)),\bigl(\textsf{codemod},\;H(\langle\text{find},\text{replace},\text{prefix},\text{grant},p\rangle),\;\kappa(p,x)\bigr),(codemod,H(⟨find,replace,prefix,grant,p⟩),κ(p,x)), where ⟨⋅⟩\langle\cdot\rangle⟨⋅⟩ encodes the tuple with a length prefix on each component, and with κ\kappaκ sufficient for search. Proof. CpC_pCp​ is a deterministic function of the partition content, the arguments and the grant. The length-prefixed encoding is injective, so by Assumption 2.1 the digest determines the four arguments and the partition prefix ppp, and κ\kappaκ determines the subtree. The prefix is needed: CpC_pCp​ lists full paths and is filtered by the job’s prefix and grant, so two partitions with the same subtree under different prefixes have different outputs, which is the defect of Section 7 in another form. This is idempotent re-execution of a deterministic task [11, Section 3.3], the purpose that Delta’s transaction identifiers serve for writes [13]. Theorem 5.3 applies with this key and map function. ◻

The grant must be part of the key because candidate filtering depends on it. Omitting it would let one caller’s stored changes be reused for a caller with a narrower grant, which is the same defect as in Section 7 with an access-control consequence. Partition-level retry is not implemented.

10 Semantic partitioning and the plan DAG

Directory partitions organize derived data. Agent work needs a finer partition. The companion paper separates the maintenance plan, a DAG over work items, from the program’s dependency graph, which may have cycles, and requires cyclically dependent changes to be grouped into a joint stage [21]. YonedaRepo implements this as a planning operation over symbol-level read and write sets (txlog/plan.rs, exposed as POST /plans). The platform plans; it does not run the work.

Definition 10.1 (Plan inputs). A work item is a tuple (i,bi,Ri,Wi)(i,b_i,\mathsf{R}_i,\mathsf{W}_i)(i,bi​,Ri​,Wi​) of an id, an optional base version and declared read and write sets of path, prefix and symbol entries (Part I, Definition 4.4). The symbol graph at the plan revision is a directed graph Gs=(N,E)G_s=(N,E)Gs​=(N,E) whose nodes are symbols (path,symbol path)(\text{path},\text{symbol path})(path,symbol path) and whose edges point from a symbol to the symbols it references, together with a set C\mathcal{C}C of coarse files whose symbols are unknown; no node of NNN lies in a file of C\mathcal{C}C. For an access set AAA, cov(A)⊆N\mathrm{cov}(A)\subseteq Ncov(A)⊆N is the set of nodes it covers: every symbol of every file that a path or prefix entry of AAA overlaps, and every symbol named by a symbol entry together with its nested members. An item writes the nodes in cov(Wi)\mathrm{cov}(\mathsf{W}_i)cov(Wi​) and touches the nodes in cov(Ri∪Wi)\mathrm{cov}(\mathsf{R}_i\cup\mathsf{W}_i)cov(Ri​∪Wi​).

Before planning, the method AccessSet::coarsen replaces every symbol entry on a coarse file by the whole path. This is Part I’s coarsening rule (Part I, Proposition 6.10). The planner then runs four steps.

  1. Join. Compute the strongly connected components of GsG_sGs​ with an iterative form of Tarjan’s algorithm [27]. For each component with more than one node, if some item writes a node of it and at least two items touch it, merge all items that touch it into one joint item, using union-find. A joint item’s read and write sets are the unions of its members’ coarsened sets.

  2. Closure. Add to each joint item’s reads the symbols reachable from the nodes it touches by following at most ddd reference edges forward, where ddd is the requested closure depth. Call the result its effective reads R^\hat{\mathsf{R}}R^.

  3. Order. Let item kkk feed item lll when Wk⋈R^l\mathsf{W}_k\bowtie\hat{\mathsf{R}}_lWk​⋈R^l​. Compute the components of the feed relation with Tarjan’s algorithm and order the items topologically over their condensation, breaking ties between components by the smallest input position of their members and ordering the members of one component by input position. Every choice depends only on input positions.

  4. Stage. Process items in that order. For each item lll, set its stage to one more than the largest stage of any earlier item kkk that is not independent of lll under the effective sets, and record kkk in the list of items lll must follow; items with no such predecessor get stage 0.

Theorem 10.2 (Plan properties). For any inputs, the plan returned by plan satisfies the following.

  1. Every input item belongs to exactly one joint item.

  2. Two distinct joint items in the same stage are independent under their effective read sets and write sets.

  3. For every pair of distinct joint items that are not independent, one is in the other’s list of predecessors and has a smaller stage.

  4. If joint item kkk feeds joint item lll and they lie in different components of the feed relation, then stage(k)<stage(l)\mathrm{stage}(k)<\mathrm{stage}(l)stage(k)<stage(l).

  5. The stage of an item is the number of items on the longest chain of predecessors ending at it, minus one. With unit durations and at least as many workers as the largest stage size, executing the stages in order finishes in exactly as many time units as there are stages, which equals the critical-path term of the companion paper’s [21, Eq. 2] bound for the DAG of recorded predecessor edges.

Proof. (a) Union-find starts with one class per input item and only merges classes, and the joint items are its final classes. (b) and (c). Let kkk precede lll in the processing order. If they are not independent, the stage step records kkk as a predecessor of lll and sets stage(l)≥stage(k)+1\mathrm{stage}(l)\ge\mathrm{stage}(k)+1stage(l)≥stage(k)+1. Independence is symmetric, as the property test eq1_is_symmetric checks and as the definition makes evident. So every non-independent pair is ordered, with strictly increasing stage, and no two such items share a stage. (d) The order step places every component of the feed relation before the components it feeds. So kkk precedes lll. Feeding means Wk\mathsf{W}_kWk​ overlaps R^l\hat{\mathsf{R}}_lR^l​, so the pair is not independent, and (c) gives the inequality. (e) The stage step computes stage(l)=max⁡{stage(k)+1}\mathrm{stage}(l)=\max\{\mathrm{stage}(k)+1\}stage(l)=max{stage(k)+1} over predecessors, with 0 for none, and it processes predecessors before successors. This is the longest-path layering of the predecessor DAG, so stage(l)+1\mathrm{stage}(l)+1stage(l)+1 is the length in items of the longest chain ending at lll. Items in one stage are independent by (b) and all their predecessors lie in earlier stages, so with enough workers each stage takes one time unit. The longest chain has as many items as there are stages, so the critical-path term of the bound equals the number of stages, and the schedule meets the bound. ◻

The planner groups cycles more narrowly than the companion paper’s instruction to group cyclic dependencies might suggest. It joins items only on a component that some item writes and that at least two items touch. Items that only read a cycle are not joined, which the test readers_alone_do_not_join_a_cycle checks. The plan therefore has one work item per written cycle of two or more symbols shared by several items, not one per strongly connected component of the program. Items that feed each other through their declared sets, without sharing a written symbol cycle, are not joined either. Step 3 places them in input order and step 4 gives them different stages, so the later one is planned to read the earlier one’s writes. Joining is reserved for reference cycles in the program, which no order of edits can break, while a feed cycle between declared sets is broken by choosing an order. A symbol that references itself forms no such component; two items that touch it, one of them writing it, overlap directly and are ordered into different stages by step 4.

Proposition 10.3 (Fewest stages is graph coloring). Let HHH be the undirected conflict graph whose vertices are joint items and whose edges join pairs of distinct items that are not independent. Apply the staging rule of step 4 to an arbitrary processing order of the vertices. The resulting stages form a proper coloring of HHH, and for every proper coloring of HHH with χ\chiχ colors there is a processing order under which the rule produces at most χ\chiχ stages. The fewest stages over all processing orders therefore equals the chromatic number of HHH.

Proof. For any processing order, two adjacent vertices are not independent, so the later one receives a stage larger than the earlier one’s, by the argument for Theorem 10.2(b); stages therefore color HHH properly. Given a proper coloring with colors 0,…,χ−10,\ldots,\chi-10,…,χ−1, process vertices in increasing color. A predecessor of lll is an adjacent vertex processed earlier, which has a strictly smaller color. By induction on color, a vertex of color jjj receives a stage at most jjj, so the plan has at most χ\chiχ stages. ◻

The proposition is the Gallai-Hasse-Roy-Vitaver theorem applied to the staging rule: the layers of the longest-path layering of an acyclic orientation color the graph properly, and some acyclic orientation has exactly χ(H)\chi(H)χ(H) layers [26, Théorèmes 1 and 2]. Each processing order induces an acyclic orientation of HHH, and every acyclic orientation arises from a topological order, so the proof above is the reduction. Minimizing the number of stages over all orders is as hard as graph coloring, which is NP-complete in its decision form (see [18]). The planner’s fixed order is a greedy coloring. The choice is defensible for a scheduler that must be deterministic and fast, but the stage count it reports is an upper bound on the parallel depth, not the minimum.

The planner does not range over all orders. Step 3 places a writer before every item it feeds whenever the two lie in different components of the feed relation, so the planner’s minimum is at least the chromatic number and can exceed it. Statement (e) of Theorem 10.2 is therefore optimal only for the predecessor DAG that the planner chose, and a different orientation of the conflicts could give fewer stages.

The cost of planning is dominated by the stage step. With mmm joint items it tests independence for m(m−1)/2m(m-1)/2m(m−1)/2 ordered pairs, and each test compares entries pairwise, so the step is quadratic in the number of items and quadratic in the size of their sets. Tarjan’s algorithm is linear in ∣N∣+∣E∣|N|+|E|∣N∣+∣E∣ [27]. The planning request also diffs the plan revision’s whole tree against the empty tree to list the files from which the symbol graph is built (repo-plan.ts), so its object reads grow with the repository, not with the plan.

The companion paper proves that a pure physical repartition, which moves semantic units between files without changing the semantic graph or the edit core, leaves the semantic closure unchanged [21]. The planner inherits this property only under a condition on how items are declared.

Proposition 10.4 (Representation invariance of plans). Write u⊑wu\sqsubseteq wu⊑w for symbols u,wu,wu,w when they lie in the same file and the symbol path of uuu equals or is nested in that of www. Let φ\varphiφ be a bijection between the symbols of two repository layouts such that (u,w)∈E(u,w)\in E(u,w)∈E if and only if (φ(u),φ(w))∈E(\varphi(u),\varphi(w))\in E(φ(u),φ(w))∈E, and u⊑wu\sqsubseteq wu⊑w if and only if φ(u)⊑φ(w)\varphi(u)\sqsubseteq\varphi(w)φ(u)⊑φ(w). If every entry of every work item is a symbol entry naming a node of NNN and no file containing a covered symbol is coarse in either layout, then the plan for the relabeled items over the relabeled graph is the relabeling of the original plan: the same joins, closures, order and stages.

Proof. Each planning step reads the inputs only through covered node sets, reference edges, component membership and the overlap of symbol entries. For symbol entries, overlap holds exactly when u⊑wu\sqsubseteq wu⊑w or w⊑uw\sqsubseteq uw⊑u. A bijection that preserves and reflects edges and ⊑\sqsubseteq⊑ therefore preserves and reflects overlap, covered sets and components, and coarsening does not occur by hypothesis. The reflection matters: a layout that merges two files can create an overlap that did not exist before, and a map that only preserved ⊑\sqsubseteq⊑ would miss it. Each step is therefore equivariant under φ\varphiφ, and so is their composition. ◻

The hypotheses are not decorative. A path entry covers every symbol of a file, so moving a symbol into or out of the file changes what the entry covers and can change the plan. A coarse file turns symbol entries into path entries, with the same effect. The relation ⊑\sqsubseteq⊑ is preserved and reflected when whole top-level items move between files. It is not when a layout spreads one type’s members over several files, which Rust’s multiple impl blocks permit, or merges files whose symbol paths are prefixes of one another, because symbol overlap requires the same file. A repository that wants plans independent of layout should therefore declare work at symbol granularity and keep its sources parseable.

Definition 10.5 (Symbol handle). A handle is a tuple h=(c,path,symbol path,range,digest)h=(c,\text{path},\text{symbol path},\text{range},\text{digest})h=(c,path,symbol path,range,digest) issued by a symbol read at commit ccc, where the digest is the platform digest of the symbol’s bytes in that commit.

Proposition 10.6 (Stale handles are rejected). A symbol edit with handle hhh on the head of a ref is accepted only if the symbol named by the handle exists in the head’s version of the file and the digest of its current bytes equals the handle’s digest, and only if the edited file still parses. Proof. symbol_edit in platform_code.rs looks up the symbol by its qualified path in the current file and returns STALE_HANDLE if it is missing or if its digest differs, and it returns INVALID_EDIT if the edited file does not parse. Equal digests imply equal bytes under collision resistance. ◻

The test for this property edits two symbols of one file. After another commit changes the first symbol and lands, an edit through the first symbol’s old handle is refused with STALE_HANDLE, and an edit through the second symbol’s handle succeeds (Section 14).

The handle check protects an edit only until its commit is created. Between creation and landing, protection comes from Part I’s validation. The edit commit declares the whole file as its read set, so any later landing that touched the file, including a change to a different symbol, makes the edit’s landing a stale read. Declaring path#symbol instead would admit concurrent edits to different symbols of one file, at the price of trusting the symbol derivation of the other commit; Part I’s validation narrows a later entry’s writes to symbols only when the platform derived them.

The symbol tables behind handles and plans are built by pure-Rust parsers, syn for Rust and oxc for TypeScript and JavaScript, running inside the Worker. The design notes had planned tree-sitter in Containers. The deviation buys determinism, local testing and the absence of a Container round trip, and it costs language coverage: only Rust, TypeScript and JavaScript files have symbols, and every other file is coarse. The platform’s WebAssembly build, which includes these parsers, is 5.0 MB.

An evaluator that prunes derivation jobs by touched paths (Proposition 5.7) looks up only the uuu changed partitions per job. Its lookup cost λ~c u cℓ\tilde\lambda_c\,u\,c_\ellλ~c​ucℓ​ does not depend on ggg and moves into kkk. That leaves b=λqNcℓb=\lambda_q N c_\ellb=λq​Ncℓ​, which is smaller, so the optimum g∗g^*g∗ is smaller: when jobs stop paying a lookup per partition, finer partitions become cheaper.

The model is a structural hypothesis, as the companion paper says of its own scalar model. Its assumption that uuu does not depend on ggg fails for very small partitions, where a commit that touches several nearby files spans several partitions. Its value here is diagnostic. It says that the implemented rule, one partition per top-level directory, fixes ggg by the repository’s layout rather than by the rates and costs that determine g∗g^*g∗. A repository whose code sits under one top-level directory has a single partition, and every commit re-indexes all of it. A repository with thousands of top-level directories pays thousands of lookups per query. The cap of 20,000 files per partition makes the first case worse: the partition is skipped, not split, so the whole directory becomes unsearchable.

A recursive partitioning removes the dependence on layout without losing content addressing. If the whole tree has at most ggg files, it is one partition. Otherwise make a directory rrr a partition root when its subtree has at most ggg files and its parent’s has more, and make a file whose parent directory has more than ggg files a partition of its own. A directory partition keeps its subtree id as key, made sufficient by repair (b) of Proposition 7.2. A file partition is keyed by its mode and blob id in a fixed-width encoding, its segment records the empty relative path, and the reduce substitutes the file’s path. Both keys are sufficient because the relative segments depend only on the content the key names. Pruning needs more care than in Proposition 5.7, because boundaries now depend on counts.

Proposition 11.2 (Pruning under size-bounded partitions). Let ccc have first parent c′c'c′ and touched paths Wv\mathsf{W}_vWv​, and let AAA be the set of directories that are proper prefixes of some path in Wv\mathsf{W}_vWv​, including the root. Under the size-bounded rule, every partition of ccc whose key is not the key of a partition of c′c'c′ is rooted at a member of AAA or at a child of a member of AAA.

Proof. A count changes between c′c'c′ and ccc only for directories in AAA, since every other directory contains no touched path. The set AAA is closed under taking parents, and the root is in AAA whenever Wv\mathsf{W}_vWv​ is nonempty, which covers the single-partition case. Whether a directory rrr other than the root is a partition root depends only on the file counts of rrr and of its parent. Take such a partition of ccc whose root’s parent is not in AAA; then r∉Ar\notin Ar∈/A either. Both counts are unchanged, so rrr is a partition root in c′c'c′, and its subtree is unchanged, so its key is a key of c′c'c′. Whether a file fff is a partition depends only on the count of its parent ddd. If fff is touched, then d∈Ad\in Ad∈A. If fff is untouched and d∉Ad\notin Ad∈/A, the count of ddd and the mode and content of fff are unchanged, so fff is a partition of c′c'c′ with the same key. In every remaining case the partition is rooted at a member of AAA or at a child of one. ◻

The derivation job must therefore list the directories in AAA and their children, not only the subtrees under touched paths. An untouched sibling can become a partition because its parent’s count crossed ggg, as when files are added elsewhere under the same parent.

The listing costs no more tree reads than the commit itself. Each tree in AAA already records the name, mode and id of every child, so reading the trees of AAA yields the children’s keys; a child’s own tree is read only to build a missing segment or to count files that are not yet memoized. The directories in AAA are the trees that preparing the commit already rewrites (Part I, Proposition 4.3), and the file count of a subtree is a content-local value that can be memoized under the subtree id. The parameters cic_ici​ and cℓc_\ellcℓ​ have not been measured, so g∗g^*g∗ cannot yet be computed for any repository; Part III, Section 9 includes the measurement.

The representation invariance of semantic closure has a counterpart for derived data. By Theorem 5.3, the answer of any content-local kind with a sufficient key and a reduce that sorts by path is the same for every partitioning. Partitioning changes cost, not results. That separation is what allows granularity to be tuned per repository without a correctness argument for each setting.

12 Vacuum

Vacuum is the platform’s only maintenance job and the only job that removes anything. Every recorded commit keeps a hidden ref refs/yoneda/c/<commit> in the object store so that the store cannot collect it while it may still land (Part I invariant I6, Part I, Table 3).

Proposition 12.1 (Vacuum safety). A vacuum run releases the hidden ref of a commit xxx only if xxx is not pinned and either (a) xxx landed on a branch at a version no later than the version at which that branch is currently projected to the object store, with the projection in sync, or (b) xxx never landed, was recorded before the start of the retention window, which defaults to seven days and is never shorter than one minute, has no pending landing, no check run queued or running within the window, is not a repair commit and is not a candidate of a running bisect. In case (a), xxx is reachable from the projected head of that branch at the time of the vacuum.

Proof. The adapter (repo-vacuum.ts) deletes hidden refs only for the commits that the authority’s plan in vacuum.rs returns, and then reports the accepted deletions; the authority’s record step does not recheck them. The two cases are the two selection queries of that plan, each of which excludes pinned commits. For (a), let uuu be the version at which xxx landed. The head at uuu is either xxx, after a fast-forward, or a platform merge commit with xxx among its parents. The platform never rewrites a landed commit: a Rebase or Merge outcome of validation, and a combiner batch, each append a merge commit whose parents are the previous head and the landed commits (Part I, Definition 4.15 and Definition 7.1). The projected version is at least uuu, and by Part I, Theorem 5.4 the head at the projected version reaches the head at uuu by first parents. So xxx is reachable from the projected head. ◻

The safety condition has the shape of Delta Lake’s vacuum, which deletes a removed data file only after a retention period that defaults to seven days [13]. Two assumptions differ: Delta’s rule is time-based, while case (a) is based on reachability, and Delta deletes files, while vacuum here only releases a reference.

Vacuum never deletes an object; it removes only the hidden ref, and collection is the object store’s decision. Case (a) rests on Part I’s invariant I12, that refs only advance along first-parent chains, which holds for the commands of the authority at cfa4845. A future command that resets or deletes a branch would have to exclude the commits it strands from case (a). The repository’s test checks that an unprojected commit is not released, that a projected one is released once, and that its content stays readable (Section 14).

15 Related work

Incremental view maintenance updates a materialized view after its base data change, instead of recomputing it, on the heuristic that only part of the view changes [16, Section 1]; see also [5, 17]. DBSP turns a query in a rich language into an incremental program, QΔ=D∘Q∘IQ^\Delta=D\circ Q\circ IQΔ=D∘Q∘I, whose linear parts run in time proportional to the change [6]. These methods differentiate the query. Repository derived data rarely admit that: a trigram index of a changed directory is cheaper to rebuild than to patch, and blame is a fold rather than a query. The scheme here recomputes the changed partitions exactly and reuses the rest. It is the linear, partition-granular case of DBSP’s theory, with the change detected by key comparison.

Build systems and self-adjusting computation memoize function results under hashes of their inputs. Mokhov, Mitchell and Peyton Jones classify build systems by their scheduler and their rebuilder [23]. Their deep constructive traces file each result under a hash of the task’s terminal inputs and are correct only for deterministic tasks [23, Section 4.2.4]. Key sufficiency is the requirement that the hash cover every input, stated for partitioned derived data. The prefix defect of Section 7 is the classic build-system error of a task reading an input, here its own location, that its key omits.

Repository systems apply the idea to version control. Mononoke separates core data written at commit from derived data computed afterwards, derives each changeset’s value from its parents’, stores derived roots under versioned keys and backfills in topological order or by slices [25]; its Bonsai changesets list file changes against parents [24]. The Scion post describes the same separation and a single generic mechanism for recursive derived data, including blame, path history and commit-graph skip lists [2]. YonedaRepo differs in using Git trees as the unit of reuse. That choice gives cross-branch and cross-fork reuse for content-local kinds at no extra cost (Proposition 5.8) and makes the key’s sufficiency a property of the tree rather than of the history. It leaves blame and path history without memoization, where Scion and Mononoke have it.

Two data-system precedents shape the job model. Resilient distributed datasets recover lost partitions from lineage because the transformations are deterministic and coarse-grained [28], and the segment key plays the role of lineage here. Delta Lake reconstructs table state from a checkpoint and the log entries after it [3, 13]. The segment store is the analogous checkpoint for derived state: a query at any commit reads stored segments for unchanged partitions and computes the tail. Unlike a Delta checkpoint, a segment is shared by every commit that contains its subtree, not tied to one version.

The plan DAG relates to scheduling with conflicts. Tarjan’s algorithm [27] supplies the joint items, and Proposition 10.3 connects stage minimization to graph coloring [18]. The companion paper supplies the independence condition and the critical-path bound that the planner realizes [21].

16 Limitations

The formal results are about the model, and the model abstracts the code. Theorem 5.3 assumes deterministic map functions, a single writer per key namespace and a store that returns only values written to it. We checked these by reading the code; we did not verify them mechanically. The theorem also says nothing about availability: a job that fails part-way leaves correct segments behind but no answer.

The prefix defect was found by analysis. Its core, equal keys with different segments, was then executed in a test outside the repository (Appendix B). Its consequences for search responses and codemods were traced through the TypeScript adapter and not run; a workerd test that renames a top-level directory and searches again would confirm that part.

The evidence for the performance claims is thin. The work bound counts tasks and lookups but not their duration. The only measured cost of derived data is the commit-time derivation phase, measured on a branch build from a single client, and the seed figures come from a commit message. The tests show that the counts behave as the proposition predicts on a three-partition repository; they do not show that partition reuse saves time on a repository of realistic size.

The execution model is not yet distributed. In the reference implementation every partition of a job runs in one Worker invocation, so the Spark analogy holds for the data model and for recovery but not for fan-out. A repository with many large changed partitions would exhaust one invocation’s connections and subrequests before it exhausted the platform.

Several derived kinds fall short of the practice the Scion post describes: blame and path history are recomputed per query, commit-graph skip lists are not built, copies are not detected and renames are detected only when content is unchanged. The implementation also narrows the model in two places. Partition granularity is fixed by layout rather than chosen, and symbols exist only for Rust, TypeScript and JavaScript.

The plan DAG is a planning artifact. The platform reports stages and stale reads, and agents decide what to run. The companion paper’s prediction that dependency-aware scheduling reduces makespan relative to file-disjoint scheduling has been demonstrated on one scripted case and not measured.

17 Conclusion

Treating source control as a transactional abstraction makes derived data a question of view consistency, and this Part answers it for partitioned views. Partitioned derived data over immutable snapshots is correct under one condition: the key under which a partition’s result is stored must determine that result. When it does, reuse equals recomputation under any interleaving of jobs, the work per commit is bounded by the changed partitions, and content addressing reuses strictly more than recursion from parents. When it does not, reuse fails silently, and YonedaRepo’s search key fails in exactly this way for renamed and duplicated directories. The repair is small and provably correct. The same discipline extends to write jobs, where a codemod is serializable when it declares its directory scope as a read, and to the plan DAG, whose stages meet the critical-path bound for the order chosen and whose plans are independent of file layout when work is declared at symbol granularity. The foundation lets every derived product of a repository, from search to the plan DAG over agents’ work, be specified as a view with a key and checked for sufficiency before it is built, on any realization of the primitives. What remains open is quantitative: the costs that fix the optimal partition size, and the savings that partition reuse delivers on repositories of realistic size.

//! Checks for the search partition key at commit cfa4845 (scratch test, not in the repository).
use base64::{Engine, engine::general_purpose::STANDARD};
use serde_json::{Value, json};
use yoneda_core::git_object::{
    FileMode, ObjectId, ObjectKind, TreeEntry, encode_tree, hash_object,
};
use yoneda_platform::platform_compute as compute;

fn tree(entries: &[(&str, FileMode, ObjectId)]) -> (ObjectId, Value) {
    let list: Vec<TreeEntry> = entries
        .iter()
        .map(|(n, m, id)| TreeEntry {
            name: (*n).into(),
            mode: *m,
            id: *id,
        })
        .collect();
    let id = hash_object(ObjectKind::Tree, &encode_tree(&list).unwrap());
    let json = entries
        .iter()
        .map(|(n, m, id)| json!({ "name": n, "type": if *m == FileMode::Tree { "tree" } else { "blob" }, "id": id.hex() }))
        .collect::<Vec<_>>();
    (id, Value::Array(json))
}

fn partitions(root: ObjectId, trees: &Value) -> Vec<Value> {
    compute(json!({ "op": "search_plan", "root": root.hex(), "trees": trees }))
        .unwrap()["partitions"]
        .as_array()
        .unwrap()
        .clone()
}

fn segment_paths(p: &Value, trees: &Value, blobs: &Value) -> Vec<String> {
    let out = compute(
        json!({ "op": "index_partition", "tree": p["tree"], "prefix": p["prefix"],
        "shallow": p["shallow"], "trees": trees, "blobs": blobs }),
    )
    .unwrap();
    out["segment"]["files"]
        .as_array()
        .unwrap()
        .iter()
        .map(|f| f["path"].as_str().unwrap().to_string())
        .collect()
}

#[test]
fn duplicate_and_renamed_directories_share_a_key_but_not_a_segment() {
    let content = b"fn retry_with_backoff() {}\n";
    let blob = hash_object(ObjectKind::Blob, content);
    let blobs = json!({ blob.hex(): STANDARD.encode(content) });
    let (sub, sub_json) = tree(&[("lib.rs", FileMode::Blob, blob)]);

    // One commit with two identical top-level directories a/ and b/.
    let (root, root_json) =
        tree(&[("a", FileMode::Tree, sub), ("b", FileMode::Tree, sub)]);
    let trees = json!({ root.hex(): root_json, sub.hex(): sub_json.clone() });
    let parts = partitions(root, &trees);
    assert_eq!(parts.len(), 2);
    assert_eq!(
        parts[0]["key"], parts[1]["key"],
        "a/ and b/ get the same storage key"
    );
    let (pa, pb) = (
        segment_paths(&parts[0], &trees, &blobs),
        segment_paths(&parts[1], &trees, &blobs),
    );
    assert_eq!(pa, vec!["a/lib.rs"]);
    assert_eq!(pb, vec!["b/lib.rs"]);
    assert_ne!(pa, pb, "the segments under that key differ");

    // A rename of src/ to lib/ with unchanged content keeps the key.
    let (r1, r1_json) = tree(&[("src", FileMode::Tree, sub)]);
    let (r2, r2_json) = tree(&[("lib", FileMode::Tree, sub)]);
    let t1 = json!({ r1.hex(): r1_json, sub.hex(): sub_json.clone() });
    let t2 = json!({ r2.hex(): r2_json, sub.hex(): sub_json });
    let (p1, p2) = (partitions(r1, &t1), partitions(r2, &t2));
    assert_eq!(
        p1[0]["key"], p2[0]["key"],
        "renamed directory keeps its key"
    );
    assert_eq!(segment_paths(&p1[0], &t1, &blobs), vec!["src/lib.rs"]);
    assert_eq!(segment_paths(&p2[0], &t2, &blobs), vec!["lib/lib.rs"]);

    // Repair (b): paths relative to the partition root make equal keys carry equal segments.
    let strip = |paths: Vec<String>, prefix: &str| -> Vec<String> {
        paths
            .into_iter()
            .map(|p| p.strip_prefix(&format!("{prefix}/")).unwrap().to_string())
            .collect()
    };
    assert_eq!(strip(pa, "a"), strip(pb, "b"));
}
